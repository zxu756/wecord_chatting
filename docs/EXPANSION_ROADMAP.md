# WeCord 拓展路线图

> 基线：`wecord-foundation` @ `85b5112`（2026-10-18）。
> 依据：
> - `docs/WECORD_FEATURES.md`、`docs/design/wecord-design-language.md`；
> - 逐节核对文档与代码（第 1 节）；
> - 调研 17 款产品 2024–2026 年的功能：微信、QQ、Telegram、WhatsApp、Signal、iMessage、LINE、Kakao、Discord、Slack、飞书、钉钉、Teams、Notion、Linear、小红书、Instagram；
> - 技术可行性调研：端到端加密、推送、多平台、LiveKit、可观测性、Realtime、语义搜索、变现、翻译。
>
> 本文回答「做什么、为什么、怎么做、先做哪些」。开工规则在 `docs/EXPANSION_BUILD_PROMPT.md`，包括并行方式、迁移规范、测试、合并上线和安全红线。
> 文中标「据调研」的价格、日期和政策会变，落地前以官方页面为准。

## 0. 读法

- **编号**：
  - A 核心聊天 · B 社交与内容 · C 圈子运营 · D 协作与效率
  - E 语音、视频、直播 · F AI · G 隐私、安全、信任 · H 多平台
  - I 开发者生态 · J 商业化 · K 运营与可观测性 · L 性能、离线、无障碍、国际化
- **每个功能写 6 项**：用户价值 / 参考 / 实现思路 / 工作量 / 依赖与风险 / 和现有功能的关系。
- **工作量**：
  - **S**：一个迁移以内、1–2 个界面，一个 subagent 半轮能做完。
  - **M**：新表 + RPC + 若干界面 + 测试和截图，一个 subagent 一轮。
  - **L**：要拆成 2 个 subagent，或者做两轮。
  - **XL**：跨多批，需要外部服务、审计或付费账号。
- **标记**：【花钱】要付费；【Apple 账号】需要付费 Apple 开发者账号；【需决定】要你拍板（产品方向、合规或隐私）。
- **已有功能不重复列**：已有的部分只在「和现有功能的关系」里说明怎么复用。

## 1. 现状核对：文档和代码不一致的地方

核对方式：两个只读 subagent 按章节核对 `WECORD_FEATURES.md` 第 0–23 节，我再抽查关键项。下面只列有出入的条目，其余数字和规则都对得上（见 1.3）。

### 1.1 文档写错或写过头（建议改文档）

1. **已读回执**
   - 文档：「私聊显示『已读』」。
   - 代码：群聊也会显示。只要任一其他成员读到最后一条，就显示「已读」。`chat_thread_screen.dart` 的 `_latestOutgoingReadState` 和 `showReadReceipt` 都没有判断会话类型。
   - 群里这样显示容易误导。A6 会改成「N 人已读」。
2. **话题「管理员可归档/锁定」**
   - 代码只有归档（`set_thread_archived`），没有锁定的列或函数。
   - C5 会补上锁定。
3. **封禁「含期限」**
   - `ban_circle_member` 只有理由和「顺带删除最近 N 小时消息」，`circle_bans` 没有 `expires_at`。
   - 有期限的是超时（禁言）。C5 会补上限期封禁。
4. **发现页「最热、最活跃、按分类和标签筛选」**
   - 实际是「热门（成员多 + 近期活跃）」和「新上架」两个分区，加分类筛选芯片和搜索框。
   - 标签只能搜索，没有标签筛选。
5. **已知限制「约 38 个 postgres_changes 订阅仍是公共通道」**
   - 实测 `onPostgresChanges(` 有 54 处调用，分布在 13 个文件，约 24 个公共通道。
   - 6 个私有通道只用 broadcast/presence。
6. **测试数量「约 3822 个」**
   - 静态能数到约 3182 个用例定义：Flutter `test(` 1663 + `testWidgets(` 1305 + Deno 214。另有 29 个 SQL 行为脚本。
   - 3822 可能是运行时数（含循环和参数化），建议以 `flutter test` 的实际输出为准。
   - 「278 个测试文件」只算了 Dart。全部算上是 333 个：278 个 Dart + 26 个 Deno + 29 个 SQL。
7. **设计语言文档朋友圈部分写「No video yet」**
   - 实际已支持一个短视频：`moments_posts.kind` 有 `video`，见 `202610190022_moments_video.sql`。
   - 设计文档这段已过时。
8. **文档日期「截至 2026-10-20」**
   - 今天是 2026-10-18，迁移编号已经排到 `202610200010`，比日历早两天。
   - 新迁移编号必须比它大，见第 8 节的编号分配。

### 1.2 代码里有、文档没写（容易让人以为没做）

1. **会话操作**：置顶聊天、标为未读、隐藏聊天（`conversation_members.pinned_at / manual_unread_at / hidden_at`）。竞品调研就曾据文档误判「WeCord 没有标为未读」。
2. **圈子标签**（类似 Discord 的 Server Tags）：圈子可设标签和 10 种徽记，成员可以把它显示在名字旁（`profiles.display_circle_tag_id`、`circle_tag_repository.dart`）。
3. **圈子帖子举报**（`report_circle_post`）。文档说「只能举报用户和公开圈子」，漏了这一项。
4. **拍一拍的两个限制**：每人每小时还有 100 次总限额；自定义后缀最多 20 字。
5. **AutoMod 的两个细节**：
   - 编辑后的消息也会检查。
   - 「时间窗口内消息数」是独立的 `spam` 规则，不属于 `mention_spam`。
6. **AI 的两个细节**：
   - 还有两个可选变量 `AI_MAX_INPUT_CHARS`、`AI_EXTRA_HEADERS`。
   - 改写和翻译支持 6 种语言（en/zh/ja/ko/es/fr），不止界面的中英文。
7. **pg_cron 实际有 7 个任务**：
   - `wecord-later-dispatch`、`wecord-purge-expired-messages`、`wecord-expire-message-files`、`chat-event-due-reminders`、`chat-event-reminders-purge`、`client-errors-purge`、`wecord-ai-guard-sweep`。
   - 活动提醒有两条路径：一是 `scheduled-dispatch` 里的 RPC；二是独立的 `chat-event-due-reminders` cron 加 `chat-event-reminders` 函数。
8. **权限清单不全**：还有 `manage_circle`、`ban_members`、`moderate_members`、`view_audit_log`、`mute_members`、`deafen_members`、`move_members`、`administrator`。
9. **群活动提醒**：创建时选「1 小时前」和/或「15 分钟前」，不是两个都固定发。
10. **未列入文档的文件**：`docs/superpowers/`（12 个计划、5 个设计）、`docs/EXPANSION_SESSION_PROMPT.md`、`tool/quick_look_demo/`。

### 1.3 已核对一致（摘要）

- **规模**：607 个 Dart 文件、175,402 行；147 个迁移；16 个 Edge Function（名字一致）；39 个功能目录。
- **数值上限**：
  - 图片 2560px、头像 512px、横幅 1600px；
  - 文件和语音 50MB，头像和横幅 20MB；
  - 草稿防抖 400ms、多选 100 条、任务负责人 10 人、群二维码 7 天、数据导出 24 小时一次；
  - 朋友圈 2000 字、9 张图、一个 ≤60 秒的视频，缩略图 480px；
  - 实时位置 15 分钟/1 小时/8 小时，非精确时模糊约 500 米。
- **规则**：合并转发的全部规则；AI 守护的分类、扣留和标记；Web Push 合并与认领；12 款壁纸。
- **未实现**：消息级举报确实还没有。

## 2. 影响全局的约束（规划前必须知道）

| 约束 | 事实 | 对路线图的影响 |
|---|---|---|
| 私聊只限好友 | `get_or_create_direct_conversation` 要求双方是好友 | 没有陌生人私信，「消息请求」不急。反垃圾重点在加好友、拉群和圈子。 |
| 通知偏好只存在本机 | `notification_preferences_repository.dart` 用 `SharedPreferences` | 免打扰时段这类功能要先把偏好搬到服务器（A4）。 |
| 举报只入库、没人处理 | `reports` 有 open/reviewed/dismissed 状态，但没有平台管理员角色，也没有处理界面 | 用户多了，或上架 App Store 前（准则 1.2 要求「举报 + 及时处理」），必须补 K1 和 A1。 |
| 聊天页过大 | `chat_thread_screen.dart` 有 8474 行 | 这是合并冲突的主要来源。先拆开并建立扩展点（L1）。 |
| 后台调度 | 新的「到点推送」接到 `run_later_dispatch()` → `scheduled-dispatch` | 不另开 cron。纯统计类（每日聚合）可以在调度里按「每天一次」守卫执行。 |
| Supabase 套餐 | 当前单文件上限 50MB，与 Free 档上限一致。据调研：Free 档 Realtime 并发 200、每秒 100 条；Pro 25 美元/月起，并发 500，可调大文件上限，有每日备份 | 大文件（会员权益）、日志导出、时间点恢复（PITR）都要先升级。【花钱】 |
| AI 能力 | 当前模型 `deepseek-v4.1-flash`，OpenAI 兼容接口 | 是否支持图片输入、是否有嵌入（embeddings）接口都**未核实**。F7 图片审核、F9 语义搜索、L8 图片描述要先确认或换供应商。 |
| Apple 免费账号 | 没有 APNs、TestFlight、通用链接、公证、PushKit；描述文件 7 天过期 | H5–H11、G11、E8 放进「待开通账号批」。 |
| LiveKit Cloud | 据调研：Build 免费档每月 5,000 参与者分钟、Egress 60 分钟；Ship 档 50 美元/月起 | 录制、直播、服务端字幕要先看用量。E1 用本机识别，可以不升级。 |
| 中国大陆合规 | 大陆区上架需要 ICP 备案。生成式 AI、带「舆论属性」的社交功能、数据出境（Supabase 和 LiveKit 都在境外）都要法务确认 | 默认不开大陆区。涉及的功能标【需决定】。 |

## 4. 各方向详细说明

### A 核心聊天体验

#### A1 消息级举报（举报给版主 / 平台）

- **用户价值**：遇到骚扰、诈骗、色情或刷屏时，可以直接举报这条消息，不必举报整个人或整个圈子。
  - 圈子里的举报先交给本圈版主。
  - 私聊和群聊的举报交给平台（K1）。
  - 上架 App Store 也需要：准则 1.2 要求有举报入口并及时处理。
- **参考**：
  - Discord「举报给版主」：服务器内的举报进版主队列。
  - WhatsApp：举报时附带最近几条消息，可「举报并拉黑」。
  - Telegram：2024 年起按原因细分举报界面。
  - Instagram：举报后可以同时限制或拉黑。
- **实现思路**：
  - **新表 `message_reports`**：
    - 字段：`id, reporter_id, message_id, conversation_id, circle_id, reason, details, snapshot jsonb, context jsonb, status (open|actioned|dismissed), handled_by, handled_at, resolution`。
    - `snapshot`：举报时的正文、附件元数据、发送者和时间。消息之后被撤回或过期也能处理。
    - `context`：只存举报者自己看得到的前后各 ≤5 条，用 `message_visible_to_current_user` 判断。
  - **RLS**：举报者只能看自己的举报；圈子举报由有 `manage_messages` 的版主看；平台举报由 K1 的 `is_app_admin()` 看。
  - **RPC**：
    - `report_message(message_id, reason, details, include_context, also_block)`：security definer。要求举报者能看到这条消息、不能举报自己、有每人每日限额；`also_block` 时顺带拉黑。
    - `list_circle_message_reports(circle_id)`。
    - `resolve_message_report(id, action)`：动作有忽略、删除消息、超时、封禁；版主的操作写入 `circle_audit_log`。
  - **客户端**：
    - 消息菜单加「举报」，自己的消息不显示这一项。
    - 举报弹层沿用举报用户的样式：原因单选、补充说明、「同时拉黑」开关、「附带上下文」说明。
    - 圈子的「审核」页（`circle_review_screen.dart`）加「用户举报」分组，红色计数并入审核队列徽标。
    - K1 后台加「消息举报」标签。
  - **Edge Function / 第三方**：不需要。
- **工作量**：M
- **依赖与风险**：
  - 依赖 L1（消息菜单拆出注册表）和 K1（平台队列）。
  - 快照含消息正文，属于敏感数据：只给处理人看，处理完 90 天后清除 `snapshot` 和 `context`。
  - 阅后即焚只存占位，不存媒体。
  - 被举报的人看不到是谁举报的。
- **和现有功能的关系**：
  - 复用 AI 守护的审核队列界面和徽标、审计日志、拉黑。
  - 与 `reports`（举报用户）、`report_circle`、`report_circle_post` 并存，在后台统一展示。

#### A2 编辑历史 + 编辑后复查

- **用户价值**：
  - 消息改过时，所有人都能看到改了什么，避免「先发后改」误导或抵赖，版主处理纠纷也有依据。
  - 同时补上已知限制：AI 守护放行后再编辑，不会重新检查。
- **参考**：
  - iMessage：发送后 15 分钟内最多编辑 5 次，可以展开看历史版本。
  - Signal：显示编辑历史。
  - Telegram：2024 年起显示最后编辑时间。
  - LINE：2026 年把「编辑消息」放进付费权益（WeCord 保持免费）。
- **实现思路**：
  - **新表 `message_edits`**：`message_id, version, body, mentions, edited_at`。
  - **写入方式**：在 `messages` 上加 BEFORE UPDATE 触发器，`body` 变化时写入旧版本。**不重写 `edit_message`**：它有 3 个版本，后面还有锁编辑的触发器，重写容易丢规则。
  - **RLS 与清理**：复用 `message_visible_to_current_user(message_id)`；撤回、过期清理、删号时一并删除。
  - **编辑后复查**：
    - 发送者仍在「新成员期」时，触发器把 `review_state` 重新置为待查，交给 `wecord-ai-guard-sweep` 处理。
    - AutoMod 本来就检查编辑。
  - **可选**：圈子设置「允许编辑的时限」（不限 / 15 分钟 / 1 小时 / 24 小时），超时的编辑由触发器拒绝。
  - **客户端**：「已编辑」标签可以点开历史弹层（各版本和时间，最新在上）；读屏朗读「已编辑，点两下查看历史」。
- **工作量**：M
- **依赖与风险**：
  - 每次编辑多一行，正文 ≤4000 字，存储可以接受。
  - 限时消息、阅后即焚、撤回时，历史必须一起消失。要写 SQL 行为测试。
  - 改 `review_state` 要基于 AI 守护最新的规则：`202610170090_ai_guard.sql`、`202610170091_ai_guard_hidden.sql`。
- **和现有功能的关系**：
  - 复用编辑流程（空输入框按 ↑ 编辑）、AI 守护、AutoMod。
  - 搜索只索引最新版本，`sync_message_search_entry` 不用改。

#### A3 聊天分组（文件夹）与折叠

- **用户价值**：会话多了以后，可以按「工作 / 家人 / 圈子 / 未读」切换，不用一直往下翻；不常看的群可以折叠起来。
- **参考**：
  - Telegram 聊天文件夹：自定义规则、图标、组内未读数。
  - WhatsApp 聊天筛选（2024）：未读、收藏、群组、自定义列表。
  - Kakao 聊天室文件夹和未读文件夹（2025-09）。
  - Slack 侧栏分区；微信「折叠的群聊」。
- **实现思路**：
  - **新表 `chat_folders`**：
    - 字段：`id, user_id, name, icon, sort_key, include_types text[]`（direct/group/channel）、`include_ids uuid[], exclude_ids uuid[], only_unread bool, exclude_muted bool`。
    - RLS 只允许本人读写，每人最多 20 个。
    - 只存规则，筛选在客户端做（会话列表本来就在本机）。
  - **手机端**：
    - 「消息」标题下加一行可横滑的 `WeCordChip` 分组条（全部 / 未读 / 各分组），长按分组可编辑。
    - 会话行长按「加入分组…」。
  - **电脑端**：侧栏私信列表上方放同样的芯片；会话行右键「加入分组…」。
  - **设置 → 聊天 →「聊天分组」**：管理页（新建、排序、改规则），带预设模板（未读、群聊、私聊、已静音）。
  - **折叠的群聊**：一个预设分组，在列表里显示为一行入口。
  - **未读数**：芯片显示组内未读，用灰色（`badgeUnread`）；组里有 @我 时显示红点。
- **工作量**：M
- **依赖与风险**：
  - 主要改 `lib/features/home/phone_messages_panel.dart`、`home_sidebar.dart`、`lib/features/chats/chats_screen.dart`；和 D2 在侧栏有少量冲突。
  - 多设备同步：进入页面时拉取，再订阅本人的行。
- **和现有功能的关系**：
  - 与置顶聊天、隐藏聊天、标为未读、静音并存，置顶的会话仍排在组内最前。
  - 快速切换器可以加「跳到分组」。

#### A4 免打扰时段与重要联系人

- **用户价值**：晚上或上课时段自动不推送，醒来再看；家人、星标好友或 @我的消息仍然会提醒。
- **参考**：
  - Slack 通知时间表；Teams 安静时间；iOS 专注模式的「允许的联系人」。
  - Instagram 安静模式（带自动回复）。
  - 微信对特定好友的「强提醒」；QQ「特别关心」。
- **实现思路**：
  - **新表 `user_notification_settings`**：
    - 字段：`user_id, timezone, quiet_enabled, quiet_days int[], quiet_start time, quiet_end time, allow_starred bool, allow_mentions bool, allow_calls bool, vip_user_ids uuid[]`。
    - 顺便把本机的「消息预览」等偏好搬到这张表。它们现在存在 `SharedPreferences`，服务器不知道。
  - **新函数 `in_quiet_hours(user_id, at timestamptz)`**。
  - **推送过滤**：在 `push` 和 `scheduled-dispatch` 函数里，发送前按收件人过滤。处于静默时段、又不在例外名单里的，不发推送，通知页照常记录。**不改 `claim_push_delivery`**：它已有 7 个版本，最容易丢规则。
  - **客户端**：
    - 设置 → 通知 →「免打扰时段」：开关、开始/结束时间、星期、例外（星标好友 / @我 / 来电 / 指定联系人）。
    - 好友资料页加「重要联系人（免打扰时也提醒）」。
    - 时段内，用户面板的铃铛显示一个月亮小标。
- **工作量**：M
- **依赖与风险**：
  - 时区以设备上报为准。推送已经按收件人时区格式化，可以复用那份时区数据。
  - 跨午夜的时段（例如 23:00–07:00）和夏令时要写 Deno 测试。
- **和现有功能的关系**：
  - 与「请勿打扰」在线状态、会话静音、圈子静音叠加，任一命中都不推送。
  - A7 加急可以突破免打扰，但有限额。

#### A5 自动翻译设置 + 翻译缓存

- **用户价值**：在跨语言的群和圈子里，不用一条条点「翻译」；可以选翻成哪种语言、哪些语言不用翻。
- **参考**：
  - WhatsApp 聊天内翻译（2025-09，可以整个聊天自动翻译）。
  - iOS 26 信息 App 的实时翻译：在对话顶部打开「自动翻译」。
  - Telegram Premium 翻译整个聊天，可设「不翻译的语言」。
  - Teams 的内联翻译设置。
- **实现思路**：
  - **新表 `message_translations`**：
    - 字段：`message_id, target_lang, text, model, created_at`，主键 `(message_id, target_lang)`。
    - RLS 复用 `message_visible_to_current_user`。
    - 消息编辑、撤回、过期、审核删除时由触发器清除译文。
  - **新表 `conversation_translation_prefs`**：`user_id, conversation_id, auto bool, target_lang`。用户级默认值放进 A4 的设置表，或 AI 设置。
  - **`ai` 函数新增 `translate_batch`**：
    - 一次最多 20 条，先查缓存，只翻缺的。
    - 跳过与目标语言相同的消息、纯 emoji、链接和 @提及。
    - 语言检测在客户端粗判（看汉字和拉丁字母的比例），或让模型顺带返回检测结果。
    - 计入现有的每日限额。
  - **客户端**：
    - 聊天「更多」里加「自动翻译此聊天」。
    - 消息下方用小字显示译文，带「显示原文」。
    - 设置 → AI 加「翻译成」（界面语言或 6 种语言之一）和「不翻译的语言」。
- **工作量**：M
- **依赖与风险**：
  - 成本低。据调研，LLM 翻译每百万字符约 0.1–0.3 美元。为防刷，只翻屏幕上看得到的消息。
  - 缓存表里有消息内容，必须跟着消息的生命周期删除。要写行为测试：过期、撤回、审核中的消息不可读。
- **和现有功能的关系**：
  - 复用 `lib/features/ai/ai_translation.dart`、AI 总开关和「圈子关闭 AI」设置：圈子关了 AI 就不自动翻。
  - 与「复制图片中的文字 → 翻译」共用同一条翻译通道。

#### A6 群已读名单 + 提醒未读的人

- **用户价值**：
  - 发了通知后，知道谁看了、谁还没看，并且可以一键提醒没看的人。
  - 顺便修正群聊里「任一人读了就显示已读」的误导。
- **参考**：钉钉已读/未读名单和 DING 未读成员；飞书群消息已读人数；WhatsApp「消息信息 → 已读者」。
- **实现思路**：
  - **数据已经有**：`conversation_members.last_read_message_id`。
  - **新 RPC `get_message_read_status(message_id)`**：
    - 只有发送者能调，只在 ≤200 人的群可用。
    - 比较方式：成员 `last_read` 指向的消息，其 `created_at` ≥ 本消息即算已读。
    - 尊重拉黑。
  - **已读回执开关**：新增 `user_privacy_settings.send_read_receipts`。关掉的人显示为「未知」，自己也看不到别人的（WhatsApp 的规则）。
  - **新 RPC `remind_unread(message_id)`**：给未读的人发推送，并在通知页生成「提醒」卡片。每条消息只能提醒一次。
  - **客户端**：
    - 群里自己发的消息底部用灰色显示「3 人已读」，点开是名单弹层：已读 / 未读两栏，加「提醒未读的人」。
    - 私聊仍显示「已读」。
    - 消息菜单加「消息信息」。
- **工作量**：M
- **依赖与风险**：
  - 大群查询开销大：限制群规模；打开名单时才查询，不实时推送计数。
  - 隐私：新增的关闭开关默认开启回执，与现状一致。
- **和现有功能的关系**：
  - 改的是 `_latestOutgoingReadState` / `showReadReceipt` 那段逻辑，L1 拆分后在独立文件里。
  - 圈子频道不做，人太多。

#### A7 加急消息与「需确认」公告

- **用户价值**：真正重要的事（集合时间改了、明天交材料）能确保对方看到；群公告可以要求成员点「已确认」。
- **参考**：飞书消息加急（应用内、短信、电话）；钉钉 DING；钉钉家校群的「通知需回执」；微信群公告。
- **实现思路**：
  - **新表**：
    - `message_urgents`：`message_id, sender_id, target_user_ids, acked_by, created_at`；每人每天最多 5 次。
    - 群公告加 `requires_ack bool`，另建 `announcement_acks`（`conversation_id, user_id, acked_at`）。
  - **推送**：
    - 加急是高优先级推送，能突破免打扰时段和静音（A4）。
    - 对方 10 分钟内没确认就再推一次，接到 `run_later_dispatch()`。
  - **客户端**：
    - 消息菜单加「加急」（选人）。
    - 收到加急时，聊天顶部出现红色横幅「xx 加急了一条消息」和「知道了」按钮。
    - 编辑公告时可以勾选「需要成员确认」；公告卡片显示「12/30 已确认」、名单和「提醒未确认的人」。
- **工作量**：M
- **依赖与风险**：
  - 红色只用在这类「需要你处理」的场景，符合设计规则。
  - 不做短信和电话加急：要接短信服务商、做实名，还要花钱。
  - 防滥用：每日限额；被加急的人可以对某个人关闭加急。
- **和现有功能的关系**：复用 A4 的免打扰判断、A6 的名单弹层、调度器。

#### A8 快捷短语与离开时自动回复

- **用户价值**：常用回复（地址、收款说明、FAQ）一键插入；休假时自动告诉别人「我不在」。
- **参考**：Telegram Business 的快捷回复、离开消息、问候消息（2024）；Instagram 安静模式的自动回复。
- **实现思路**：
  - **快捷短语**：新表 `quick_replies`（`user_id, shortcut, body`）。输入 `/` 时，快捷短语排在机器人命令前面。
  - **自动回复**：设置存在 A4 的表里（`away_enabled, away_message, away_until`）。
    - 由消息插入触发器发出，只发给私聊里的好友，24 小时内对同一人只回一次。
    - 消息标注「自动回复」。
  - **客户端**：设置 → 聊天 →「快捷短语」；自定义状态弹层里加「离开时自动回复」。
- **工作量**：S
- **依赖与风险**：群里不发自动回复；两个人都开了自动回复时不能互相刷（只回复人发的消息，不回复自动回复）。
- **和现有功能的关系**：复用斜杠命令候选列表、自定义状态（emoji + 文字 + 过期时间）。

#### A9 引用部分文字回复 + 静默发送

- **用户价值**：长消息里只针对其中一句回复；深夜发消息不吵醒对方。
- **参考**：Telegram 引用片段（2023-12）和静默消息；微信 8.0.62 的引用部分文字（据调研，灰度中）。
- **实现思路**：
  - **引用片段**：
    - `messages.reply_preview` 已经是 jsonb，在里面加 `quote` 字段（起止偏移 + 文字快照）。
    - 回复时如果选中了文字就带上；气泡里的引用块显示片段，点击跳回原消息。
  - **静默发送**：
    - 在 `messages.interaction` 里加 `silent` 标志。
    - 长按发送按钮出现「静默发送」。
    - `push` 函数读到 `silent` 时照样发，但不响铃（Web Push 的 `silent: true`）。
- **工作量**：S
- **依赖与风险**：在 `push` 函数里处理 `silent`，比改 `claim_push_delivery` 安全。
- **和现有功能的关系**：配合回复、左滑回复、定时发送（定时消息也可以选静默）。

#### A10 语音消息增强

- **用户价值**：长语音可以 1.5× / 2× 听完；能连续播放多条；录到一半能暂停；发送前可以裁剪。
- **参考**：
  - 微信语音倍速（8.0.56 起）和连续播放。
  - Telegram 暂停续录（2024-01）和裁剪（2025-06）。
- **实现思路**：只改客户端的 `lib/features/chats/voice_message_player.dart` 和 `voice_message_recorder.dart`。
  - **倍速**：用 `just_audio` 的 `setSpeed`。
  - **连播**：播放结束后，自动播放本会话里下一条未听的语音；记住每条的播放进度。
  - **暂停续录**：`record` 包支持 pause/resume。
  - **裁剪**：在发送托盘里拖动起止点；WAV 直接按采样截取。
  - **听筒/扬声器切换**：可以放到后面再做。
- **工作量**：S（倍速 + 连播）；M（加上裁剪和暂停）。
- **依赖与风险**：网页端 `record` 的暂停要验证；裁剪不需要服务器。
- **和现有功能的关系**：配合已有的语音转文字，裁剪后重新转写。

#### A11 个人表情包（收藏表情、抠图做贴纸）

- **用户价值**：
  - 看到好玩的表情图，可以「添加到表情」，以后在任何聊天里使用。
  - 自己的照片可以一键抠图做成贴纸。
  - 这是中文用户的高频需求。
- **参考**：微信「添加到表情」和表情管理；WhatsApp 贴纸制作（2024）；Telegram 从图片做贴纸；iMessage 实况贴纸（抠出主体）。
- **实现思路**：
  - **新表 `user_stickers`**：`id, owner_id, path, width, height, animated, sort_key, created_at`，每人上限 300。
  - **私有存储桶 `user-stickers`**：
    - 只有本人可写。
    - 发送时把文件复制到会话文件夹，沿用 `chat-files` 的路径规则，避免任何人都能读到别人的表情库。
  - **客户端**：
    - 图片、GIF、贴纸消息的菜单加「添加到表情」。
    - 贴纸面板加「我的」标签，带排序、删除和管理页。
  - **抠图**：
    - iPhone/Mac 用 Vision 的 `VNGenerateForegroundInstanceMaskRequest`（iOS 17+ / macOS 14+），在本机完成。
    - 网页复用背景虚化已在用的 MediaPipe 分割模型。
    - 结果存成 PNG 或 WebP。
  - **发送**：沿用现有的 `sticker` 消息类型（`messages.type = 'sticker'`），附件标注来源为个人表情。
- **工作量**：M
- **依赖与风险**：
  - 版权和违规内容靠举报（A1）兜底。
  - AI 守护只查文字，不查贴纸。
  - 动图限制在 1MB 以内。
- **和现有功能的关系**：
  - 与圈子自定义表情和贴纸并列，面板分「我的」和「本圈子」。
  - 复用图片压缩和 `MotionSafeImage`（减少动画时静止）。

#### A12 消息特效与关键词彩蛋

- **用户价值**：生日、过年时的「表情雨」带来仪式感。
- **参考**：微信关键词表情雨（发「生日快乐」下蛋糕雨）；iMessage 屏幕特效和逐词特效；Telegram 消息特效（2024-05）。
- **实现思路**：纯客户端。
  - 内置一份中英文关键词表（生日快乐、新年快乐、恭喜、想你了……）。
  - 收到或发出含关键词的消息时，在聊天上层用 `CustomPainter` 播放一次轻量粒子动画。
  - 每条消息只播一次，已播记录存在本机。
  - 减少动画时不播；设置 → 聊天加「关键词特效」开关。
  - 可选：长按发送键选特效，存在 `messages.interaction.effect`。
- **工作量**：S
- **依赖与风险**：不改服务器；粒子数要设上限；读屏不朗读特效。
- **和现有功能的关系**：可以复用通话表情的飘屏组件。

#### A13 圆形视频消息

- **用户价值**：比视频通话轻、比语音更有表情，适合打招呼和简短说明。

#### A14 共同好友 / 共同群聊 / 添加来源

### B 社交与内容

#### B1 日常（24 小时动态）+ 密友

- **用户价值**：比朋友圈更轻、更即时。拍一张就发，24 小时后消失；朋友看到可以直接回复到私聊。
- **参考**：
  - Instagram Stories 和密友名单。
  - WhatsApp 状态；微信状态；Signal Stories；Kakao「펑」。
  - Telegram Stories（2023 年起，2025 年加了相册和直播故事）。
- **实现思路**：
  - **新表**：
    - `stories`：`id, author_id, media_path, media_kind (photo|video), caption, audience, created_at, expires_at`（发布后 24 小时）。`audience` 同朋友圈：all / only_me / include / exclude，可选好友标签。
    - `story_views`：`story_id, viewer_id, viewed_at`。
    - `story_reactions`。
  - **可见性函数 `story_visible_to(story, viewer)`**：复用朋友圈 `moments_post_visible_to` 的观众模型；拉黑或删好友后立即失效。
  - **存储与清理**：私有桶 `stories`；过期清理接到 `run_later_dispatch()` 的清理阶段。
  - **回复**：回复日常 = 发一条带 `story_ref` 附件的私聊消息，显示缩略图和「回复了你的日常」。
  - **客户端（查看）**：
    - 手机首页快捷好友行：有新日常的好友头像外加一圈强调色环（**不用红色**）。
    - 点开全屏查看：进度条，点按切换，长按暂停，下滑关闭，底部有回复框和快速表情。
    - 电脑侧栏「朋友圈」一行旁显示同样的头像环。
    - 自己的日常可以看「谁看过」。
  - **客户端（发布）**：拍照或从相册选 → 复用照片编辑器（涂鸦、文字、马赛克、裁剪）→ 选观众（默认好友，可选「密友」标签）。
  - **精选**：把日常收进个人资料的「精选」（不过期），放到后面做。
- **工作量**：L
- **依赖与风险**：
  - 存储和流量：视频限 ≤15 秒、≤20MB。
  - 「谁看过」只给作者看。
  - 内容审核靠举报，A1 要扩展到日常。
- **和现有功能的关系**：
  - 复用朋友圈的观众选择表单、好友标签、照片编辑器、压缩与缩略图、私有信号通道。
  - 与朋友圈并存：朋友圈是长期的，日常是 24 小时的。

    - `circle_onboarding_prompts`：问题、是否必答、单选或多选。
    - `circle_onboarding_options`：选项对应的 `role_ids` 和 `channel_ids`。
    - `circle_member_onboarding`：成员的回答和已完成的新人任务。
    - `circle_guide_tasks`：任务标题和动作类型（去某个频道 / 读规则 / 发自我介绍 / 设置头像）。
  - **新 RPC `complete_onboarding_prompts(circle_id, option_ids)`**：
    - 按选项分配角色。这是系统动作，不走「只能管理比自己低的角色」的限制，要在审计里写清楚。
    - **只允许分配不含任何管理权限的角色。**
  - **频道可见性**：用现有的频道权限覆盖，让某些频道只对某个角色可见。
  - **客户端**：
    - 确认规则之后出现问题页（扩展 `circle_onboarding.dart`）。
    - 圈子首页顶部显示「新人指南」卡片和任务进度。
    - 管理页「引导」里可以编辑问题和任务。
    - 新人入圈的系统消息带「打招呼」按钮，点击发一个贴纸回复。
- **工作量**：M
- **依赖与风险**：角色分配涉及权限，必须防止通过引导拿到高权限角色。
- **和现有功能的关系**：扩展现有引导（必须接受规则才能发言）、角色、频道权限覆盖、欢迎消息。

#### C3 圈子数据看板

- **用户价值**：圈主看得到成员增长、留存、活跃时段、热门频道和邀请来源，知道运营有没有效果。
- **参考**：Discord Server Insights；Telegram 频道统计；飞书多维表格仪表盘。
- **实现思路**：
  - **新表**：
    - `circle_daily_stats`：`circle_id, day, members_total, joined, left, active_members, messages, voice_minutes, top_channels jsonb`。
    - `circle_member_daily`：只记录当天是否活跃，不存任何内容。
  - **聚合**：每天凌晨跑一次，在 `run_later_dispatch()` 里按「每天一次」守卫执行。这是统计不是推送，单独建一个 pg_cron 任务也可以。
  - **新 RPC `get_circle_insights(circle_id, range)`**：只给有 `manage_circle` 或 `view_audit_log` 权限的人。
  - **客户端**：圈子设置 →「数据」。
    - 图表：成员数折线、每日消息和活跃柱状、「星期 × 小时」热力图。
    - 表格：频道排行、邀请排行。
    - 用 `CustomPainter` 自绘或引入 `fl_chart`，颜色走 tokens。
- **工作量**：M
- **依赖与风险**：小圈子要防止推断出个人行为：少于 5 的数字显示「<5」，留存只给比率。
- **和现有功能的关系**：复用审计日志、成员表、语音状态；C4 提供邀请来源字段。

#### C5 版主工具 2.0

- **用户价值**：补齐日常管理：限期封禁、锁定话题、警告与版主备注、按条件筛选成员并批量处理、被封者申诉。
- **参考**：
  - Discord 成员安全页：按入服时间、账号年龄、角色筛选，可以批量处理。
  - 限期封禁类机器人；AutoMod 警告；Twitch 的解封申请。
- **实现思路**：
  - **限期封禁**：`circle_bans.expires_at`，到期由 `run_later_dispatch()` 解封并写审计。
  - **锁定话题**：话题加 `locked_at`，锁定后只有版主能发言。要改发送检查，必须基于发送路径的最新规则。
  - **版主备注**：新表 `circle_member_notes`（备注、警告次数），只给有 `moderate_members` 的人看。
  - **申诉**：新表 `circle_ban_appeals`，每次封禁只能申诉一次。

- **工作量**：M
- **依赖与风险**：做完后改正文档里「封禁含期限」「话题可锁定」的说法（见第 1 节）。
- **和现有功能的关系**：封禁和超时、话题、审计日志、AI 守护的标记。

#### C6 突袭防护

- **用户价值**：遭遇刷人或刷屏时自动「锁门」，版主同时收到告警。
- **参考**：Discord AutoMod 的突袭告警，以及「暂停邀请 / 暂停私信」安全动作。
- **实现思路**：
  - 入圈触发器统计 10 分钟内的入圈人数，超过阈值（圈子可以自己设）时：
    - 设置 `invites_paused_until`，暂停邀请；
    - 切到 C1 的 apply 模式；
    - 往告警频道发一张 AutoMod 告警卡。
  - 圈子菜单加「安全动作：暂停邀请 1 小时 / 24 小时」。
- **工作量**：S
- **依赖与风险**：大型活动时阈值可能误伤。所以只暂停邀请、不踢人，可以一键恢复。
- **和现有功能的关系**：AutoMod 告警频道、AI 守护（扣留新成员）、C1。

#### C7 成员荣誉与头衔

- **用户价值**：增加归属感和活跃度：圈主可以给成员发专属头衔；还有每周活跃榜、连续发言天数等荣誉。

#### C9 媒体频道 + 问答频道

- **用户价值**：作品类圈子（像素画、摄影）可以用图片墙浏览；求助类频道可以标「已解决」和采纳答案。

### D 协作与效率

#### D1 表单与收集表

- **用户价值**：在群里收集信息（报名信息、尺码、问卷、作业提交）不用跳到别的 App。比接龙能收更多字段，还能一键提醒没填的人、导出表格。
- **参考**：
  - 腾讯文档收集表、钉钉智能填表、飞书问卷（中文群最常用）。
  - Notion Forms（2024-10）；Linear Asks 网页表单；Google Forms。
- **实现思路**：
  - **新表 `forms`**：
    - 字段：`conversation_id, creator_id, title, description, fields jsonb, settings jsonb, closed_at`。
    - `settings` 包括：是否匿名、每人一次、可否修改、截止时间、结果可见范围（仅发起人 / 所有人提交后可见 / 所有人）。
  - **新表 `form_responses`**：`form_id, user_id, answers jsonb, submitted_at, updated_at`。
  - **字段类型**：单行文字、多行文字、数字、单选、多选、日期、图片（上传到会话文件夹）、成员（选人）。
  - **校验**：在 RPC `submit_form_response` 里检查必填、类型、选项是否合法、截止时间、人数上限。
  - **权限**：RLS 按会话可见性。匿名表单对发起人也隐藏 `user_id`：数据里存着，但查询视图不返回。
  - **客户端**：新目录 `lib/features/forms/`：
    - 创建表单：字段编辑器，可以拖动排序。
    - 表单卡片：`well` 卡片，和接龙、投票同一风格，显示「已提交 12/30」、截止时间和「填写」按钮。
    - 填写页。
    - 结果页：按人的表格、按题的统计图。
    - 「提醒未填写的人」：复用 A6 的提醒；没有 A6 时先做推送 + 通知页。
    - 导出 CSV：在客户端生成，网页直接下载，Apple 设备用分享。
  - **入口**：聊天「+」→「表单」。私聊不能发起（和接龙一样）。发起人可以关闭或重新开放。
- **工作量**：L。可以拆给两个 subagent：一个做「创建和填写」，一个做「结果和导出」。
- **依赖与风险**：
  - 图片字段要遵守存储路径规则：文件必须放在会话文件夹下。
  - 导出时不包含匿名者的身份。
  - 审批（飞书、钉钉那种）不另起功能，在 D1 之后作为表单的「需要审批」选项来做。
- **和现有功能的关系**：
  - 是接龙和投票的泛化：接龙相当于只有一行文字的表单。
  - 结果可以「转为任务清单」，每行一个任务。
  - 数据导出要包含自己提交的表单回答。

#### D2 我的日程（跨聊天聚合 + 日历订阅）

- **用户价值**：一个页面看到今天和本周所有和我有关的事：报名的活动、指派给我且快到期的任务、我设的提醒、我排好的定时消息；还能订阅到系统日历。
- **参考**：飞书日历与任务中心；钉钉待办；Slack「稍后」；Notion Calendar；Teams 日历。
- **实现思路**：
  - **新 RPC `get_my_agenda(from, to)`**：
    - 合并五类来源：`chat_event_rsvps`（去 / 可能）、`circle_event_rsvps`、`task_item_assignees`（未完成且有截止日期）、本人的 `message_reminders`、本人待发的 `scheduled_messages`。
    - 统一返回 `kind, title, starts_at, all_day, conversation_id, circle_id, target_id`。
    - 全部按现有可见规则过滤，退群后就看不到了。
  - **日历订阅：新 Edge Function `calendar-feed`**：
    - 地址形如 `GET /calendar-feed/<token>.ics`。`token` 是用户在设置里生成的随机令牌，服务器只存哈希，可以重置，令牌里不含任何用户 ID。
    - 返回未来 60 天的活动和任务；标题可以选「只显示时间，不显示内容」。
    - 在 `supabase/config.toml` 里设 `[functions.calendar-feed] verify_jwt = false`。日历 App 不会带登录令牌。
  - **客户端**：新目录 `lib/features/agenda/`：
    - 列表视图：今天 / 明天 / 本周 / 以后，逾期的标红。
    - 月历视图。
    - 入口：电脑侧栏在「收藏」附近加一行「日程」；手机首页快捷行加一格；快速切换器可以搜「日程」。
- **工作量**：M
- **依赖与风险**：令牌泄露就等于日程泄露。所以默认只输出「时间 + 会话名」，正文要用户自己勾选；令牌可以随时重置。
- **和现有功能的关系**：
  - 复用活动的 .ics 生成代码、任务、提醒、定时消息、`WhenSheet`。
  - D7 的日历视图和 C10 的重复活动做完后都会出现在日程里。

#### D3 群打卡

- **用户价值**：学习群、健身群每天打卡，显示连续天数和今天的名单。
- **参考**：QQ 群打卡；钉钉家校打卡；小红书群聊打卡。

  - 卡片显示「今日 18/30 · 你已连续 7 天」。
- **工作量**：S/M（在 D1 或接龙的基础上做）。
- **依赖与风险**：跨时区时，「一天」以发起人的时区为准。
- **和现有功能的关系**：D1、接龙、C7 荣誉（连续打卡天数）。

#### D4 重复的定时消息

- **用户价值**：每周一提醒交周报、每天早上发值日表，不用每次手动安排。
- **参考**：Telegram 重复定时消息（2025-11）；Slack 工作流的定时消息。
- **实现思路**：
  - `scheduled_messages` 加 `recurrence` 和 `recurrence_until`。
    - 规则：每天 / 工作日 / 每周几 / 每月几号。
    - 按发送者时区的墙钟时间计算，复用 `later_time.dart` 的夏令时处理。
  - `run_later_dispatch()` 发出一条后生成下一条。改这个函数要基于最新定义 `202610190021_moments_push.sql`。
  - 定时消息面板显示「每周一 9:00」这样的规则。
- **工作量**：S
- **依赖与风险**：失败重试不能导致重复发送，用 `client_id` 去重。
- **和现有功能的关系**：定时发送、`WhenSheet`；下一次发送会出现在 D2 日程里。

#### D5 笔记 2.0

- **用户价值**：笔记可以评论讨论、用模板快速开始、插入表格、导出 Markdown 或 PDF，还能发布成公开网页，分享给没有 WeCord 的人。
- **参考**：Notion 的评论、模板库、Sites 发布；飞书文档的评论和导出；Google Docs 批注；Teams Loop。
- **实现思路**：
  - **评论**：新表 `note_comments`（`note_id, block_id, anchor`（起止偏移）`, author_id, body, resolved_at`）；评论里的 @提及走通知页。
  - **模板**：新表 `note_templates`，内置会议纪要、周报、旅行计划，另外支持个人模板。
  - **表格块**：`note_blocks.kind` 加 `table`。行列存在 props 里，单元格是纯文本，三方合并按单元格进行。
  - **导出**：在客户端把块转成 Markdown（块结构现成，直接映射）；PDF 用 `pdf` 包，网页用浏览器打印。
  - **发布为网页**：`notes.published_slug`，由 Worker 只读渲染 `/n/:slug`。发布者可以撤回，网页不包含评论。
- **工作量**：L（评论 M + 模板和导出 S + 表格块 M + 发布 S）。
- **依赖与风险**：
  - 表格块要扩展 `NoteSyncEngine` 的合并规则（按单元格合并），是最复杂的部分，可以放到最后。
  - 公开发布有泄密风险：默认关闭，发布时提示「任何拿到链接的人都能看」。
- **和现有功能的关系**：在 `note_apply_ops` 和 `NoteEditor` 上扩展；与 F5 笔记 AI 共用编辑器入口。

#### D6 圈子知识库

- **用户价值**：圈子的规则、新手指南、FAQ、资源整理成有目录的文档，而不是散落在置顶消息里。
- **参考**：飞书知识库；Notion 团队空间；Discord 服务器指南的资源页。
- **实现思路**：
  - `notes` 加 `circle_id`（圈子级，不属于某个频道）和 `parent_id`（层级）。
  - 权限：圈子成员（或指定角色）可以看；有 `manage_channels` 或指定角色的人可以编辑。
  - 圈子菜单加「知识库」：左侧是目录树，编辑沿用笔记编辑器。
  - 可以设为 C2 新人任务里的「必读」。
- **工作量**：M
- **依赖与风险**：笔记权限函数（`can_current_user_*_note`）要加圈子级分支，基于最新定义改。
- **和现有功能的关系**：笔记、C2 引导；知识库也是 F1 AI 问答最好的检索来源。

#### D7 任务清单 2.0

- **用户价值**：清单字段可以自定义（数字、单选、链接、人员），支持子任务、重复任务（比如每周倒垃圾）和日历视图，小团队和家庭分工都够用。
- **参考**：飞书多维表格、Notion 数据库、Linear 的子工单和周期、Slack Lists。
- **实现思路**：
  - **自定义字段**：`task_lists.field_defs jsonb`（最多 20 个字段），`task_items.custom jsonb`。`upsert_task_item` 的按字段合并扩展到自定义字段，基于最新定义改。
  - **子任务**：`task_items.parent_id`，只支持一层。
  - **重复任务**：`recurrence`，完成后生成下一条。
  - **日历视图**：按截止日期显示，复用 D2 的月历组件。
- **工作量**：L
- **依赖与风险**：改字段类型时要兼容旧数据；离线补发队列要支持新字段。
- **和现有功能的关系**：任务清单、看板、D2 日程、D1 表单的「转为清单」。

#### D8 群标签页

- **用户价值**：把常用的链接、笔记、清单、表单固定在聊天顶部，一点就到。
- **参考**：飞书群标签页；Teams 频道标签页。
- **实现思路**：
  - 新表 `conversation_tabs`：`conversation_id, kind (note|list|form|link), target, title, sort`。管理员或有发言权的人可以添加。
  - 电脑端在聊天头部下方显示一行小芯片；手机端放在「更多」里分组显示。
  - 置顶笔记横幅可以迁移成第一个标签。
- **工作量**：S
- **依赖与风险**：头部空间有限（设计规则：头部最多 3–4 个主操作），所以用一行可横滑的标签条，默认折叠。
- **和现有功能的关系**：置顶笔记、笔记和清单面板、D1 表单。

#### D9 工作流自动化

- **用户价值**：不用写代码，就能设置「新成员加入 → 发欢迎私信并给角色」「有人点 ✅ → 创建任务」「每周五 → 发周报表单」这类规则。
- **参考**：Slack Workflow Builder；Notion 按钮和数据库自动化；Teams 工作流。
- **实现思路**：
  - 新表 `automations`：
    - 作用域：圈子或群。
    - 触发：入圈、表情回应、关键词、定时、表单提交。
    - 动作：发消息、发私信、加角色、建任务、发表单。
  - 执行：数据库触发器把任务写进 `automation_runs` 队列，由 `run_later_dispatch()` 消费。
  - 每个圈子有限额，全部可审计。
- **工作量**：L
- **依赖与风险**：
  - 以「圈子机器人」的身份执行，权限不能超过创建者。
  - 要防止规则互相触发、形成循环。
- **和现有功能的关系**：机器人、AutoMod、D1、D7；可以和 I2 事件订阅共用事件源。

#### D10 白板

- **用户价值**：在通话或群里一起画图、头脑风暴。
- **参考**：Teams Whiteboard；飞书白板；Slack huddle 里的屏幕涂鸦。
- **实现思路**：
  - 复用照片编辑器的笔画模型，做成一种笔记块或独立页面。
  - 笔画按操作 ID 同步。笔画只增不改，天然容易合并。
- **工作量**：L
- **依赖与风险**：笔画多时的性能；优先级低。
- **和现有功能的关系**：照片编辑器、笔记、通话。

### E 语音、视频与直播

#### E1 通话字幕与纪要

- **用户价值**：
  - 通话和语音频道里实时看到字幕：听不清、不方便外放、听障用户都用得上。
  - 结束后自动生成纪要和待办，存进这个会话的共享笔记。
- **参考**：Teams 实时字幕和智能回顾；飞书妙记；钉钉 AI 听记；Slack huddle 的 AI 笔记；Google Meet。
- **实现思路**：
  - **本机识别，服务器零成本**：
    - 每个参会者的设备只识别**自己的麦克风**。iPhone/Mac 复用 `voice_input` 的 `SFSpeechRecognizer` 通道，网页用 Web Speech API。
    - 识别出的句子通过 LiveKit 数据消息（可靠通道，带说话人和时间）发到房间，所有人拼成字幕条。
    - 不支持识别的设备，显示「xx 的设备不支持字幕」。
  - **同意**：
    - 字幕和纪要要由发起者开启，所有人都会看到「字幕已开启」。
    - 每个人可以选择不贡献自己的字幕。
  - **纪要**：
    - 结束时，发起者把文字记录发给 `ai` 函数的新动作 `meeting_recap`，返回要点、待办和决定。
    - 结果创建为笔记（复用 notes 的接口），并在聊天里发一张笔记卡片。
    - 待办可以一键转成任务（F4）。
  - **翻译字幕（后做）**：每人选「字幕翻成…」，句子批量翻译，复用 A5 的缓存。
- **工作量**：L
- **依赖与风险**：
  - 识别质量取决于设备，中英文混说时效果一般。
  - 不录音、不存音频，这是隐私卖点，要在文档里写清楚。
  - 如果需要统一的识别质量，再考虑 LiveKit Agents。据调研，STT 每分钟约 0.003–0.005 美元。
- **和现有功能的关系**：复用语音输入插件、LiveKit 房间、`ai` 函数、笔记、任务。

#### E2 预约通话

- **用户价值**：约好「周四晚 8 点语音开会」，到点所有报名的人都收到提醒，一点就能进。
- **参考**：WhatsApp 预约群通话；Teams 和飞书会议；Discord 活动挂语音频道。
- **实现思路**：
  - 活动加 `call_link_code`：创建活动时可选「附带通话」，生成一个现有的通话链接，有效期覆盖活动时段。
  - 开始前的提醒推送里带「加入通话」。
  - 活动进行中，活动卡片显示绿色的「正在进行 · 加入」。
- **工作量**：S
- **依赖与风险**：活动提醒的两条路径都要带上通话链接。
- **和现有功能的关系**：活动、通话链接、提醒、D2 日程。

#### E3 视频直播 【花钱】

- **用户价值**：在圈子里做分享会、教学、游戏直播，观众多也不卡；观众可以发弹幕和表情。
- **参考**：Discord Go Live；Telegram 直播（RTMP）；钉钉群直播；视频号和 Instagram Live。
- **实现思路**：
  - **阶段 1：舞台频道视频化**：
    - 主讲人可以开摄像头或共享屏幕。观众只订阅：`livekit-token` 按角色下发 `canPublish=false`。
    - 旁边是聊天栏，飘屏表情复用通话表情；显示观众人数。
  - **阶段 2**：OBS 推流（E7）。
  - **阶段 3**：观众很多时，用 Egress 输出 HLS 到 Cloudflare R2，加 CDN 分发；客户端用 `video_player` 播放 HLS，延迟约 5–30 秒。
- **工作量**：L
- **依赖与风险**：
  - 观众带宽按 LiveKit 下行计费。据调研，Ship 档超出后约 0.12 美元/GB，100 人看 1 小时约 67GB。
  - 大陆连通性差。
- **和现有功能的关系**：舞台频道（举手、邀请上台）、通话表情、屏幕共享放大。

#### E4 一起看 / 一起听

- **用户价值**：语音通话里同步看同一个视频、听同一首歌。
- **参考**：Discord Watch Together（Activities）；iMessage SharePlay；QQ 一起听歌、一起看。
- **实现思路**：
  - 通话中选「一起看」，分享一个视频链接：
    - 直链的 MP4 或 HLS 用 `video_player` 播放；
    - YouTube、B 站只能内嵌网页播放器，能控制的东西有限。
  - 主持人的播放、暂停、拖动通过 LiveKit 数据消息广播；其他人对齐时间戳，误差超过 1 秒就纠正。
- **工作量**：M
- **依赖与风险**：
  - 版权：只同步播放控制，不转发媒体流。
  - 各平台网页播放器的接口限制。
- **和现有功能的关系**：通话、悬浮小窗、应用内浏览器。

#### E5 通话录制 【花钱】【需决定】

- **用户价值**：重要会议留档，缺席的人可以回看。
- **参考**：Teams 会议录制和逐字稿；Kakao 通话录音转写（2025）；LINE 2026 年付费权益里的通话录音。
- **实现思路**：
  - LiveKit Egress 录制（房间合成 MP4，或只录音频），写入 S3 兼容存储。Cloudflare R2 最省，没有出站流量费。
  - 新函数 `recordings`：开始和停止录制，只给发起者或版主。
  - 录制时所有人都看到红点「正在录制」。这里用红色合理：需要你注意。
  - 录好的文件进会话的群文件（B6），保留期限可以设置。
- **工作量**：L
- **依赖与风险**：
  - 费用：Egress 转码分钟（据调研，Ship 档超出后视频约 0.02 美元/分钟）加存储。
  - 需要你定录制同意规则和保存期限（GDPR、PIPL）。
- **和现有功能的关系**：通话、E1（有了录音，转写可以更准）、B6。

#### E6 语音频道状态 + 网络质量提示 + 仅音频模式

- **用户价值**：语音频道能写一句「正在打排位」；网络差时有提示，可以一键切到仅音频。
- **参考**：Discord 语音频道状态（2023）；Teams 网络质量指示。
- **实现思路**：
  - `circle_channels.voice_status`：最多 60 字，频道里的人可以改，频道列表里显示。
  - LiveKit 的 `ConnectionQuality` 显示在自己的头像上。
  - 「仅音频」= 取消订阅所有视频轨。
- **工作量**：S
- **依赖与风险**：无。
- **和现有功能的关系**：语音频道、悬浮小窗。

#### E7 OBS 推流（RTMP / WHIP 推入） 【花钱】

- **用户价值**：主播可以用 OBS 等专业软件推流到舞台频道。
- **参考**：Telegram 直播支持 RTMP。Discord 没有这个功能，只能共享屏幕。
- **实现思路**：用 LiveKit Ingress。新函数为主讲人生成推流地址和密钥。WHIP 不转码，免费；RTMP 要转码，按分钟计费。
- **工作量**：M
- **依赖与风险**：RTMP 转码要花钱；推流密钥可能泄露，所以用一次性密钥，并且可以吊销。
- **和现有功能的关系**：E3。

#### E8 系统画中画 【Apple 账号】

- **用户价值**：离开 App 时，通话视频仍然以系统小窗显示。现在只有应用内小窗。
- **参考**：FaceTime 和 WhatsApp 视频通话的画中画。
- **实现思路**：
  - iOS 用 `AVPictureInPictureController`，加上视频通话专用的 `AVPictureInPictureVideoCallViewController`（iOS 15+）。
  - 要写原生插件，把远端视频帧渲染进去。
  - 后台使用摄像头需要 iOS 16+ 的「多任务相机访问」entitlement，要向 Apple 申请。
  - macOS 用独立浮窗代替。
- **工作量**：M
- **依赖与风险**：entitlement 要付费账号才能申请；Flutter 这边要自己写插件。
- **和现有功能的关系**：悬浮小窗、通话。

### F AI

#### F1 AI 问答（问聊天记录，带出处）

- **用户价值**：问「上周群里定的聚餐地点是哪？」「圈子里谁推荐过那款耳机？」，直接得到答案，还能点出处跳回原消息。
- **参考**：Slack AI 搜索答案和企业搜索（2025）；飞书知识问答；Notion Q&A；钉钉 AI 搜问；小红书「点点」。
- **实现思路**：
  - **阶段 1（不需要向量）：`ai` 函数新动作 `ask`**：
    1. 让模型把问题改写成 2–3 组关键词。
    2. 用现有的 `search_messages` 在用户可见范围内检索，最多 50 条。它已经遵守过期、审核中、无权限频道等全部规则。
    3. 把这些消息作为**不可信数据**交给模型回答，要求它引用消息 ID。
    4. 客户端把引用渲染成可以点的出处卡片。
  - **阶段 2**：接入 F9 的混合检索（全文 + 向量），提高召回。
  - **范围**：默认只查当前会话或当前圈子；全局问答需要用户主动选择。
- **工作量**：M（阶段 1）
- **依赖与风险**：
  - 每次提问计入每日限额。
  - 提示注入（聊天里写「忽略之前的指令」）：沿用现有的隔离做法。
  - 回答只能基于检索到的消息，找不到就说找不到。
- **和现有功能的关系**：搜索页加「问 AI」切换；复用补课总结的提示词安全框架和「圈子关闭 AI」开关。

#### F2 @AI 助手（在群里召唤）

- **用户价值**：在群里 @WeCord AI「帮我们整理一下刚才的方案」「把这段翻成英文」「列个分工」，所有人都能看到回答。
- **参考**：
  - Telegram Guest AI Bots（2026-05）：机器人不必是群成员，只看得到被 @ 的消息和回复。
  - LINE Agent i（2026）；腾讯元宝在群里；Meta AI 在 WhatsApp 群里；钉钉 AI 助理。
- **实现思路**：
  - **身份**：建一个系统机器人账号「WeCord AI」，复用 `bots` 的独立身份机制（`profiles.is_bot`）。它不用加入群，被 @ 时以它的身份回复。
  - **触发**：
    - 消息插入触发器检测到提及 AI 后，写入 `ai_jobs` 队列。
    - 由 pg_net 唤醒 `ai` 函数的新动作 `assistant`，和 AI 守护的唤醒方式相同。
  - **上下文**：
    - 只给模型三样东西：被 @ 的那条消息、它回复的那条、发起人看得到的最近 N 条。
    - N 由发起人选：仅这条 / 最近 20 条 / 最近 100 条。
    - 系统提示固定隔离聊天内容。
  - **能力**：回答、总结、翻译、改写、列待办。列待办用 F4 的结构化输出，卡片上有「转成任务」。
  - **开关**：圈子关了 AI 就不响应；群主可以在群设置里关掉；每人有每日限额。
- **工作量**：M
- **依赖与风险**：
  - 内容安全：AI 的回复也要能被举报（A1）。
  - 成本随使用量增长。
  - 面向大陆公众的生成式 AI 需要备案。【需决定】
- **和现有功能的关系**：复用机器人身份、提及、`ai` 函数的服务商切换和限额、AI 守护的唤醒链路。

#### F3 每日速览

- **用户价值**：每天早上收到一份「你关注的群和频道昨天发生了什么」，忙的时候不用逐个翻。
- **参考**：Slack AI 每日回顾（Recaps）；Kakao Kanana 未读摘要；LINE OpenChat 的 AI 摘要。
- **实现思路**：
  - 新表 `ai_digest_subscriptions`：`user_id, conversation_ids`（最多 10 个）`, deliver_at time, timezone`。
  - `run_later_dispatch()` 到点把任务放进队列。
  - `ai` 函数按会话调用现有的 `summarize`（最近消息或未读模式），汇总成一张通知页卡片，并推送「今日速览已就绪」。
  - 只总结用户当时看得到、未过期、不在审核中的消息。
- **工作量**：S/M
- **依赖与风险**：
  - 成本随订阅数线性增长，所以每人最多 10 个会话，没有新消息就不调用。
  - 关了 AI 的圈子跳过。
- **和现有功能的关系**：复用补课总结、调度器、通知页（新增卡片类型）。

#### F4 AI 提取待办与日程

- **用户价值**：讨论完一键得到「谁、做什么、什么时候」，确认后直接变成任务或活动。
- **参考**：Teams 智能回顾里的待办；飞书妙记待办；LINE Agent i 计划中的「从聊天抽取日程」；iOS 26 由 AI 建议发起投票。
- **实现思路**：
  - `ai` 函数新动作 `extract_actions`，输出结构化 JSON：`title`、`assignee`（成员 ID，只能从会话成员里选）、`due`、`kind`（task / event）。
  - 入口：多选消息后点「提取待办」，或在 F2 里调用。
  - 结果在弹层里逐条确认、修改，然后调用 `upsert_task_item` 或创建活动。
- **工作量**：S
- **依赖与风险**：
  - 模型给出的人名要严格映射到成员，找不到就留空。
  - 时间按发起人时区解析，复用时间令牌的解析器。
- **和现有功能的关系**：多选、任务清单、活动、时间令牌。

#### F5 笔记 AI

- **用户价值**：在笔记里续写、总结、改语气、生成提纲、翻译整篇、从笔记里提取待办。
- **参考**：Notion AI；飞书文档 AI；Teams Copilot in Loop。
- **实现思路**：
  - 入口：笔记编辑器的 `/` 菜单加「AI…」；选中文字后，格式栏加 ✨。
  - `ai` 函数新动作 `note_assist`，模式有 continue / summarize / outline / tone / translate / extract_tasks。
  - 结果以「插入到下方」或「替换选中」的方式应用，作为普通块操作走 `note_apply_ops`，可以撤销，会进历史版本。
- **工作量**：S/M
- **依赖与风险**：长笔记会被截断（`MAX_TEXT_CHARS = 8000`）。
- **和现有功能的关系**：改写（同一套模式）、笔记编辑器、任务清单。

#### F6 AI 回复建议 / 按上下文起草

- **用户价值**：不知道怎么回时，给出 2–3 个建议，或者根据上下文起草一段回复再修改。
- **参考**：WhatsApp 起草回复（2026-03）；钉钉 AI 灵动回复；LINE Agent i 回复建议；Gmail 智能回复。
- **实现思路**：
  - 输入框 ✨ 菜单加「帮我回复」。
  - 把最近 20 条（用户可见的）和用户的意图（可选，一句话）发给 `ai` 函数的新动作 `draft_reply`。
  - 结果填进输入框，不自动发送。
- **工作量**：S
- **依赖与风险**：不默认开启「自动建议」，以控制成本和隐私；只在用户点击时调用。
- **和现有功能的关系**：改写按钮、AI 限额。

#### F7 AI 守护 2.0 【需决定】图片模型

- **用户价值**：
  - 新成员发的图片、投票、活动、笔记标题也会被检查。
  - 放行后再编辑会复查（和 A2 一起）。
  - 私聊里收到疑似诈骗时有提示。
- **参考**：Telegram 2026 年的 AI 守护机器人（审核入群）；Discord 青少年安全助手和敏感媒体过滤；微信、WhatsApp 的反诈提醒。
- **实现思路**：
  - **扩大检查范围**：AI 守护的分类入口扩展到投票问题、活动标题和说明、笔记标题、任务标题（已知限制里列出的这几项）。
  - **图片**：如果 AI 服务商支持图片输入，就把 480px 缩略图送检；不支持就不做。
  - **诈骗预警**：**非好友**在群和圈子里发来的消息，如果含收款、转账、验证码、链接等关键词，显示黄色提示条「谨防诈骗：对方不是你的好友」。先用规则，可选再加 AI。
- **工作量**：M
- **依赖与风险**：
  - 要不要换支持图片的模型需要你定。`deepseek-v4.1-flash` 是否支持图片输入未核实。
  - 误报会打扰正常用户，所以只提示、不拦截。
- **和现有功能的关系**：AI 守护、AutoMod、A2（编辑后复查）、G5。

#### F8 Apple 设备本机 AI

- **用户价值**：在 Mac（以及支持的 iPhone）上，总结、改写、翻译可以完全在本机完成，不上传、不占额度。以后的私密聊天（G9）尤其需要。
- **参考**：Apple Foundation Models 框架（iOS 26 / macOS 26）；WhatsApp Private Processing；Kakao Kanana Nano。
- **实现思路**：
  - 写 Swift 插件调用 Foundation Models，实现 `summarize`、`rewrite`、`translate` 三个接口。需要 Apple Intelligence 设备：Apple 芯片的 Mac，或 iPhone 15 Pro 及以后的机型。
  - `AiRepository` 增加「本机」提供方。
  - 设置 → AI 加「优先使用本机 AI」。
- **工作量**：M
- **依赖与风险**：
  - 只有新设备可用；本机模型能力较弱，长对话要分段处理。
  - 你现在的 iPhone 设备 ID 开头是 `00008120`，推测是 A16 芯片，不支持 Apple Intelligence，只能在 Mac 上测。
  - 框架本身不需要付费账号，但要用 macOS 26 / iOS 26 的 SDK 构建。
- **和现有功能的关系**：在 `ai` 函数之外提供第二条路径；G9 私密聊天里只允许用本机 AI。

#### F9 语义搜索（向量） 【花钱】

- **用户价值**：搜「上次说的那家日料」，也能找到写着「寿司店」的消息。
- **参考**：Slack AI 搜索；Notion Q&A；飞书知识问答。
- **实现思路**：
  - **存储与索引**：pgvector，`halfvec(1024)` 列加 HNSW 索引。
  - **生成流水线**：用 Supabase 的「自动嵌入」方案：pgmq + pg_cron + pg_net + 一个 `embed` 函数。
  - **嵌入模型**：选支持中文的 bge-m3 或 Qwen3-Embedding。据调研，每百万 token 约 0.01 美元。
  - **嵌入范围**：只嵌入值得检索的内容（笔记、长消息、按会话窗口切块），不逐条嵌入短消息。
  - **查询**：函数用 `security invoker`，先按可见会话过滤；再和全文检索做 RRF 混合排序。
- **工作量**：L
- **依赖与风险**：
  - 主要成本是数据库内存。据调研，100 万条 1024 维向量加索引约 3–4GB，需要更大的计算规格。
  - OpenCode Go 是否提供嵌入接口未核实。
  - 私密聊天的内容无法嵌入。
- **和现有功能的关系**：F1 的阶段 2、全局搜索、D6 知识库。

### G 隐私、安全与信任

#### G1 隐私权限 2.0：谁能加我、谁能拉我进群、怎样找到我

- **用户价值**：不想被陌生人加好友、不想被随便拉进群时，自己说了算。
- **参考**：
  - 微信「加我为朋友时需要验证」「添加我的方式」「群聊邀请确认」。
  - WhatsApp「谁可以把我加进群组」。
  - Telegram 隐私设置（谁能拉我进群、谁能给我打电话）。
- **实现思路**：
  - **新增设置**：`user_privacy_settings` 加以下字段：
    - `friend_request_from`：所有人 / 朋友的朋友 / 共同圈子成员 / 没有人；
    - `discoverable_by_username bool`、`discoverable_by_qr bool`；
    - `group_invite_from`：所有好友 / 星标好友 / 需要我同意；
    - `allow_calls_from`。
  - **改动点（都基于最新定义）**：
    - 发好友请求的 RPC 检查 `friend_request_from`。
    - 用户名搜索遵守 `discoverable_by_username`。
    - `add_group_members`（`202605180005_social_chat_v2.sql`）：对方要求同意时，改为创建 `group_invitations`。通知页出现卡片「xx 邀请你加入 yy」，可以接受或拒绝，7 天过期。
  - **客户端**：
    - 设置 → 隐私与安全，新增「加好友」「群邀请」「通话」三组，用 `showOptionPicker`。
    - 通知页的「好友」芯片里显示群邀请卡片。
- **工作量**：M
- **依赖与风险**：
  - 私聊本来就只限好友，这是现有的强约束，**不要放开**。
  - 改 `add_group_members` 时，要保证群二维码、名片这些自愿加入的路径不受影响。
- **和现有功能的关系**：好友请求、群聊、通知页、拉黑；和 A14 共用「朋友的朋友」的计算。

#### G2 应用锁与聊天锁

- **用户价值**：手机借给别人时，App 或某几个聊天要用面容、指纹或密码才能打开；锁住的聊天还可以从列表里藏起来。
- **参考**：WhatsApp 聊天锁和秘密代码（2023）；Telegram 密码锁；Signal 屏幕锁；QQ 隐藏会话（2026）。
- **实现思路**：
  - **验证方式**：用 `local_auth` 插件，iOS 用 Face ID / Touch ID，macOS 用 Touch ID；网页用应用内 PIN。
  - **应用锁**：切到后台超过 N 分钟，回来要解锁。
  - **聊天锁**：
    - 本机设置锁哪些会话、是否在列表里隐藏；隐藏的会话要在搜索框输入秘密代码才会显示。
    - 这是设备级保护，不需要服务器。
  - **推送**：锁住的会话推送不显示内容。为此要把「隐藏推送内容」同步到服务器，复用 A4 的设置表。
- **工作量**：S/M
- **依赖与风险**：
  - 网页上的 PIN 只是遮挡，不是加密，要说明清楚。
  - 忘了 PIN 就退出登录，再重新登录。
- **和现有功能的关系**：隐藏聊天（已有）、A4、通知预览开关。

#### G3 登录提醒

- **用户价值**：账号在新设备上登录时立刻知道；不是自己登录的，可以一键踢下线。
- **参考**：Telegram、WhatsApp、Discord 的新登录通知。
- **实现思路**：
  - 由 `sessions` 函数，或 `user_devices` 新增时的数据库触发器，通知其他设备：
    - 推送；
    - 通知页「安全」卡片：设备名、平台、时间。不显示 IP 和位置，和设备管理一致。
  - 卡片上有「不是我」按钮：登出那台设备，并引导去改密码。
- **工作量**：S
- **依赖与风险**：首次登录不提醒；令牌刷新不算新登录，避免误报。
- **和现有功能的关系**：设备管理、推送、通知页。

#### G4 两步验证恢复码 + 通行密钥（Passkey）

- **用户价值**：丢了验证器 App 也能找回账号；用面容或指纹登录，不怕钓鱼和撞库。
- **参考**：GitHub、Google 的恢复码；Telegram 通行密钥登录（2025-12）；WhatsApp 用通行密钥加密备份（2025-10）。
- **实现思路**：
  - **恢复码**：
    - 开启 TOTP 时生成 10 个一次性恢复码，只存哈希（`mfa_recovery_codes`）。
    - 新函数 `mfa-recovery` 验证恢复码后，用 Auth Admin API 删除这个用户的 TOTP 因子。
  - **通行密钥**：取决于 Supabase Auth 是否已支持 WebAuthn 登录（需核实）。支持之前，不要自己实现 WebAuthn 服务端。
- **工作量**：M
- **依赖与风险**：恢复函数必须限速并记审计。
- **和现有功能的关系**：两步验证、G3。

#### G5 反诈提示与链接安全检查

- **用户价值**：点开可疑链接前有提醒；陌生人发来的「中奖」「代付」消息有警示。
- **参考**：微信、WhatsApp 的反诈提示；Discord 可疑链接警告；iOS 26 未知发件人筛选。
- **实现思路**：
  - `link-preview` 函数顺带返回风险等级：本地黑名单，可选再查 Google Safe Browsing API。
  - 高风险链接在应用内浏览器打开前，先出现提示页。
  - 非好友的诈骗提示条见 F7。
- **工作量**：S/M
- **依赖与风险**：Safe Browsing 的商用条款要确认，可以先只用本地规则。
- **和现有功能的关系**：链接预览、应用内浏览器、F7。

#### G6 高级聊天隐私

- **用户价值**：敏感话题的群可以禁止转发、保存媒体、导出和 AI 读取。
- **参考**：WhatsApp 高级聊天隐私（2025-04）；Telegram 禁止转发与保存（2026-03 扩展到私聊）。
- **实现思路**：
  - **开关**：`conversations.restrict_sharing`。私聊里任一方开启就生效；群里由管理员设置。
  - **服务端**：对这个会话拒绝转发、合并转发、收藏、数据导出、AI 总结和翻译。
  - **客户端**：隐藏对应的菜单项；媒体不能保存到相册；显示提示条「此聊天已开启高级隐私」。
- **工作量**：M
- **依赖与风险**：
  - 截屏无法阻止，和阅后即焚一样要说明。
  - 改动面广：转发、合并转发、收藏、导出、AI 全部要加检查。
- **和现有功能的关系**：可以复用阅后即焚「不能转发」的规则；A5 和 F 系列的 AI 功能都要遵守。

#### G7 截屏提示

- **用户价值**：阅后即焚的照片被截屏时，发送者能知道。
- **参考**：Telegram 秘密聊天的截屏通知；Snapchat。
- **实现思路**：
  - iOS 监听 `userDidTakeScreenshotNotification`；录屏时遮挡阅后即焚的内容。
  - 截屏时调用 `report_view_once_screenshot(message_id)`，聊天里出现系统提示「对方截屏了」。
  - macOS 和网页检测不到，要说明。
- **工作量**：S
- **依赖与风险**：只能提示，不能阻止。
- **和现有功能的关系**：阅后即焚。

#### G8 本地缓存加密

- **用户价值**：手机或电脑上的聊天缓存即使被拷走，也读不出来。
- **参考**：Signal（SQLCipher）；WhatsApp 本地数据库加密。
- **实现思路**：
  - 把 `sqflite` 换成 SQLCipher 版本（`sqflite_sqlcipher` 或 `sqlcipher_flutter_libs`），密钥放在系统钥匙串里（`flutter_secure_storage`）。
  - 网页的 IndexedDB 无法真正保护，要说明。
  - 同时评估把 Supabase 登录会话从 `shared_preferences` 移到安全存储。
- **工作量**：M
- **依赖与风险**：
  - 现有缓存直接清空重建即可，缓存本来就能重新生成。
  - macOS 钥匙串在免费签名下只能在本机运行。
- **和现有功能的关系**：离线缓存、发件箱。

#### G9 端到端加密（分阶段） 【需决定】

- **用户价值**：重要的私聊连服务器也读不到。这是 WeCord 目前隐私承诺里最大的缺口。
- **参考**：
  - Signal：Signal 协议；2025 年推出后量子三棘轮 SPQR，2026 年推出自动密钥验证。
  - WhatsApp 默认端到端加密；iMessage 的 PQ3。
  - Telegram 秘密聊天：可选开启，绑定设备。
  - Discord DAVE：基于 MLS 的音视频端到端加密。
- **实现思路**：
  - **阶段 0（M）**：
    - 写威胁模型和产品话术，说明「元数据不加密」。
    - 通话媒体端到端加密：用 LiveKit 帧加密，`livekit_client` 已支持，网页要编译 `e2ee.worker.dart.js`。
    - 密钥由双方设备用 X25519 协商，服务器不经手明文。
  - **阶段 1（XL）：私聊可选开启「私密聊天」**：
    - 协议库首选 `openmls`（MIT 许可，原生支持多设备和群组）。网页走 WASM，但不支持 Flutter 的 `--wasm` 构建。
    - 备选 `libsignal`（AGPL 许可，要律师确认）。
    - Supabase 只负责投递：密钥包表、密文消息、Realtime。
    - 恢复口令：用 Argon2id 包装私钥，密文存在服务器上。网页必须有恢复流程。
    - 私密聊天里关闭：服务器搜索；AI（只允许 F8 本机 AI）；服务器链接预览（改由发送方生成）；推送预览（只显示「新消息」）；合并转发；AutoMod。
  - **阶段 2（L）**：小群端到端加密；本地搜索（L3）。
  - **阶段 3**：做完外部密码学审计后，才在宣传里说「端到端加密」。
- **工作量**：XL
- **依赖与风险**：
  - 现有的 Dart 绑定都是个人维护、没有审计过。
  - 密钥丢失就等于历史丢失。
  - 和 AI、搜索这些卖点冲突。
  - App Store 准则 1.2 要求「过滤和举报」。私密聊天里只能靠用户举报时自愿附上明文。
- **和现有功能的关系**：
  - 几乎所有服务端功能都要加「私密聊天跳过」的分支。
  - 先做 G8（本地加密）和 L3（本地搜索），会降低难度。

#### G10 社区准则、隐私政策与年龄声明 【需决定】最低年龄

- **用户价值**：用户知道什么不能发、数据怎么用；版主和平台处理举报有依据。上架 App Store 也需要。
- **参考**：Discord 社区准则；Telegram 服务条款；Apple 准则 1.2 和 5.1.1。
- **实现思路**：
  - 网页路由 `/legal/guidelines`、`/legal/privacy`、`/legal/terms`。内容用 Markdown，随应用打包，中英两版。
  - 注册页勾选「我已满 X 岁并同意……」；记录 `profiles.accepted_terms_at` 和 `age_confirmed_at`。
  - 设置里加「关于」入口；举报弹层里链接到社区准则。
- **工作量**：S
- **依赖与风险**：
  - 最低年龄（13+ / 16+ / 18+）和要不要做青少年模式，需要你定。
  - 条款内容我们只能起草，需要你确认。
- **和现有功能的关系**：A1 和 K1 的处理依据；说明数据导出和删除账号。

#### G11 敏感图片模糊 【Apple 账号】

- **用户价值**：收到可能是裸露内容的图片时先模糊，点开才显示。尤其适用于圈子里非好友发来的图片。
- **参考**：Apple 敏感内容警告（`SensitiveContentAnalysis` 框架，iOS 17+）；Discord 敏感媒体过滤；Instagram 青少年账号。
- **实现思路**：
  - iOS 和 macOS 用 `SCSensitivityAnalyzer` 在本机分析收到的图片。用户需要在系统设置里打开敏感内容警告。
  - 网页和其他平台：对「圈子里非好友发来的图片」默认模糊，用户可以关闭。
- **工作量**：M
- **依赖与风险**：这个框架需要 entitlement `com.apple.developer.sensitivecontentanalysis.client`，免费账号拿不到。
- **和现有功能的关系**：图片消息、F7。

### H 多平台

#### H1 Android

- **用户价值**：Android 用户用上原生 App，推送、通话、扫码都更顺。
- **参考**：所有对照产品都有 Android 版。
- **实现思路**：
  - **阶段 0（S，现在就能做）**：
    - Android Chrome 已经能安装 PWA 并收到 Web Push。
    - 做一次 Android 网页适配检查并修问题：返回键、键盘遮挡、语音输入（Web Speech）、相机扫码、文件上传、点通知后的跳转。
  - **阶段 1（L）：原生 App**：
    - 用 `flutter create --platforms=android` 补齐 Android 工程。
    - 权限和前台服务：要声明 `microphone`、`camera`、`mediaProjection`、`phoneCall` 类型。Android 14 起必须声明类型，而且麦克风类前台服务不能在后台启动。
    - 通知：建 4 个通知渠道（消息、@提及、来电、后台常驻）；Android 13+ 要在运行时申请 POST_NOTIFICATIONS。
    - 推送：用 `firebase_messaging`，Edge Function 走 FCM HTTP v1（服务账号 JWT 用 WebCrypto 签名）。新表 `native_push_tokens`（`user_id, platform, token, device_id, locale, timezone`）；`push` 和 `scheduled-dispatch` 增加 FCM 分支。
    - 语音转写走服务端的 `AI_TRANSCRIBE_*`：Android 的本机识别依赖 Google 服务，大陆设备用不了。
    - 图片文字识别：用 ML Kit，或者先隐藏。
    - Office 预览：走 Gotenberg，和网页一样。
    - 背景虚化：用 MediaPipe，或者先隐藏。
    - Krisp 有 Android 版。
    - `flutter_webrtc` 的 release 包要加 ProGuard 规则。
  - **阶段 2：分发**：
    - 直接发 APK，免费。
    - 或上 Google Play：一次性 25 美元；新的个人账号要先找 12 名测试者连续封闭测试 14 天。
- **工作量**：阶段 0 是 S；阶段 1 是 L。
- **依赖与风险**：
  - 上 Play 要花钱。
  - 大陆设备没有 GMS，用不了 FCM，厂商推送通道要另外接。
  - 国产 ROM 会杀后台。
- **和现有功能的关系**：
  - 所有 `kIsWeb` / `Platform.isIOS` 分支都要补上 Android。
  - 推送从「只有 Web Push」变成多通道，为 H5（APNs 经 FCM）铺路。

#### H2 Windows 桌面 【需决定】

- **用户价值**：Windows 用户有原生窗口、托盘和通知。现在只能用 PWA。
- **参考**：微信、QQ、Discord、Slack 的 Windows 客户端。
- **实现思路**：

- **依赖与风险**：

#### H5 原生推送（APNs）+ 通知快捷回复 + 角标 【Apple 账号】

- **用户价值**：iPhone 和 Mac 上 App 关着也能收到消息。现在基本收不到，这是已知最大的体验缺口之一。
- **参考**：所有原生聊天 App。
- **实现思路**：
  - **通道**：开通付费账号后创建 APNs 的 `.p8` 密钥。二选一：上传到 Firebase，`push` 统一走 FCM v1（和 H1 共用出口）；或者在 Edge Function 里直接签 ES256 JWT 调 APNs。
  - **令牌**：`native_push_tokens` 记录 iOS 和 macOS 的设备令牌。
  - **通知分类**：
    - 消息：快捷回复（`UNTextInputNotificationAction`）、标为已读。
    - 来电。
    - 提醒。
  - **角标**：数字 = 未读会话数，由服务器计算，随推送下发。
  - **预留**：加 Notification Service Extension，以后私密聊天解密用。
- **工作量**：M
- **依赖与风险**：需要付费账号；密钥要设成函数密钥，由你自己运行我们给的 `! supabase secrets set ...` 命令。
- **和现有功能的关系**：推送的「认领一次」机制、按语言和时区生成的推送文字、A4 免打扰。

- **和现有功能的关系**：私聊和群通话、通话链接、悬浮小窗。

#### H7 TestFlight 分发 【Apple 账号】

#### H8 App Store 上架准备 【Apple 账号】【需决定】

- **用户价值**：任何人都能从 App Store 下载。
- **参考**：Apple《App 审核指南》1.2（用户生成内容）和 5.1.1(v)（应用内删除账号）；Discord、Telegram 在 iOS 上的举报和屏蔽流程。
- **实现思路**：对照审核准则自查：
  - 准则 1.2：举报（A1）、拉黑（已有）、内容过滤（AutoMod、AI 守护）、公开联系方式、及时处理（K1）。
  - 准则 5.1.1(v)：应用内删除账号（已有）。
  - 隐私营养标签：列出收集的数据（账号、位置、错误报告等）。
  - 年龄分级：社交和 UGC 类一般较高。
  - 准备审核用账号和演示说明。
  - 大陆区默认不选，因为需要 ICP 备案。
- **工作量**：M
- **依赖与风险**：要你定是否上大陆区、最低年龄。
- **和现有功能的关系**：依赖 A1、K1、G10 先完成。

- **和现有功能的关系**：接在现有的 `flutter build macos` 之后。

#### H10 通用链接 + Android App Links 【Apple 账号】仅 iOS 部分

### I 开发者生态

#### I1 交互组件 + 交互回调

- **用户价值**：机器人可以发带按钮、下拉选择、表单弹窗的消息（审批、投票机器人、小游戏），不只是文字。
- **参考**：Slack Block Kit；Discord 消息组件（2025 年的 Components V2）；飞书消息卡片；Telegram 内联键盘；Teams Adaptive Cards。
- **实现思路**：
  - **数据**：`messages.components jsonb`，用严格的 schema：按钮（最多 5 行 × 5 个）、单选下拉、链接按钮。不允许任意 HTML。
  - **点击**：调用 RPC `submit_interaction(message_id, component_id, values)`，写入 `bot_interactions`。这张表已经存在，先看清它现在的用途。
  - **机器人收到点击**：二选一：通过 Bot API 长轮询拉取（类似 Telegram 的 `getUpdates`），或由 I2 的 Webhook 推送。
  - **机器人回复**：可以发「只有点击者看得到」的临时消息（`ephemeral_for`），或者编辑原消息。
- **工作量**：L
- **依赖与风险**：
  - 临时消息需要新的可见性规则：在 `message_visible_to_current_user` 的最新定义上加分支。
  - 防滥用：点击要限速。
- **和现有功能的关系**：Bot API、斜杠命令、`bot_interactions`、I2。

#### I2 事件订阅（出站 Webhook）

- **用户价值**：机器人和外部服务能实时收到「新消息、@提及、成员加入、表单提交」等事件，不用轮询。
- **参考**：Slack Events API；Telegram `setWebhook`；Discord Gateway 和交互端点。
- **实现思路**：
  - **新表**：
    - `bot_event_subscriptions`：`bot_id, url, events[], secret`。
    - `bot_event_deliveries`：投递队列，记录事件、状态、重试次数、下次重试时间。
  - **流程**：数据库触发器入队 → `run_later_dispatch()` 唤醒新函数 `bot-events` → 投递。
  - **投递规则**：带 HMAC-SHA256 签名头；超时 5 秒；失败按指数退避重试 5 次；只投递机器人有权看到的频道。
- **工作量**：M
- **依赖与风险**：
  - 外部 URL 要防 SSRF：禁止内网地址。
  - 投递日志 7 天后清理。
- **和现有功能的关系**：Bot API、Webhook、调度器、D9。

#### I3 Bot API 2.0 + 开发者页面

- **用户价值**：机器人能在群和私聊里用（不只是圈子频道），能发文件、加表情回应、编辑和删除；开发者有清楚的文档和调试页面。
- **参考**：Telegram Bot API；Discord 开发者门户；Slack API 文档。
- **实现思路**：
  - **新接口**：`bot-api` 增加发文件、表情回应、编辑和删除自己的消息、话题、投票、读取成员公开信息。
  - **机器人可以进群和私聊**：
    - 拉机器人进群需要群主同意。
    - 用户可以主动私聊机器人，不需要先加好友。这个例外写在 `get_or_create_direct_conversation` 里，要基于最新定义改。
  - **文档**：把 `docs/bot-api.md` 升级成 OpenAPI 3 文件，并在 Worker 上提供文档页。
  - **开发者设置**：设置 → 开发者，包含我的机器人、令牌、最近的调用日志、事件订阅（I2）。
- **工作量**：M
- **依赖与风险**：私聊机器人打破了「私聊只限好友」，所以只对 `is_bot` 账号开放，并且必须由用户主动发起。
- **和现有功能的关系**：机器人管理、斜杠命令、I1、I2。

#### I4 小程序（内嵌网页应用） 【需决定】

### J 商业化（不碰支付牌照）

**原则**：
- 只卖「数字服务 / 虚拟物品」。钱只从用户流向平台，经 Apple IAP、Google Play 或代收商（MoR）。
- **不做**：余额钱包、真钱红包、用户之间转账、可以提现的虚拟币、给创作者分成（这些都需要支付牌照，或者会构成「二清」）。

#### J1 WeCord 会员 【花钱】【Apple 账号】【需决定】

- **用户价值**：重度用户花一点钱，换更大的文件、更多 AI 额度、更多个性化。
- **参考**：Telegram Premium（4GB 上传、翻译、语音转文字、更多文件夹和置顶、专属贴纸）；Discord Nitro；LINE LYP Premium；QQ 超级会员；Kakao 톡서랍 플러스。
- **实现思路**：
  - **建议的权益**：
    - 文件上限从 50MB 提到 1GB（需要 Supabase Pro 和 L4 断点续传）；
    - AI 每日额度 ×5；
    - 更多聊天分组和置顶；
    - 个人表情库从 300 张到 1000 张；
    - 会员专属壁纸、气泡主题、资料特效（J3）；
    - 1080p 屏幕共享；
    - 会员徽记。
    - **不**把基础的安全和隐私功能放进会员。
  - **数据**：新表 `entitlements`：`user_id, plan, source (apple|google|paddle|stripe|lemonsqueezy), status, current_period_end, original_transaction_id`；函数 `has_entitlement(user, feature)`。
  - **服务端检查**：在存储策略、AI 限额、表情上限等处检查权益。
  - **新函数**：
    - `billing-apple`：接 App Store Server Notifications V2，验证 JWS；
    - `billing-google`：接 RTDN；
    - `billing-web`：代收商的 webhook，验证签名。
  - **客户端**：设置 → 会员，显示权益表、价格、购买和恢复购买。iOS 和 Android 用 IAP（`in_app_purchase` 包），网页跳转到代收商的结账页。
- **工作量**：L
- **依赖与风险**：
  - 收款主体和所在地决定能用哪家代收商。据调研，Stripe Managed Payments 不支持中国大陆商家；Paddle 和 Lemon Squeezy 需要核实。
  - Apple 抽成 15–30%。据调研，大陆区从 2026-03 起是 12–25%。
  - 美国「外链付款免佣」的规则还在诉讼中，不要当成长期前提。

### K 运营与可观测性

#### K1 运营后台（平台管理员 + 举报处理）

- **用户价值**：
  - 你作为平台方，终于能处理举报：查看被举报的人、圈子、帖子和消息，然后警告、封号、下架圈子或删除内容，全程留痕。
  - 这也是上架 App Store 的前提。
- **参考**：各平台的信任与安全（Trust & Safety）后台；Discord 安全中心的处理流程。
- **实现思路**：
  - **数据**：
    - `app_admins`：`user_id, role (owner|moderator|support), created_at`。
    - **第一个 owner 不能写死在迁移里**。由你自己运行一条插入命令；构建提示里会给出这条 `!` 命令。
    - `is_app_admin()`、`admin_audit_log`。
    - `reports` 加 `handled_by, handled_at, resolution`。
    - `app_user_suspensions`：`user_id, until, reason`。
    - `circles.disabled_at`：下架后从发现页隐藏，并禁止加入。成员是否还能进入，需要你定。
  - **RPC**（全部 security definer，并检查 `is_app_admin()`）：
    - `admin_list_reports(kind, status)`：用户、圈子、帖子举报；A1 上线后加上消息举报。
    - `admin_resolve_report`。
    - `admin_suspend_user`：同时通过新函数 `admin` 用服务角色调用 `auth.admin.updateUserById({ ban_duration })` 封禁。
    - `admin_disable_circle`、`admin_delete_circle_post`。
  - **客户端**：
    - 隐藏路由 `/admin`。入口在设置 →「运营后台」，只有管理员看得到。
    - 设计语言 C 的纸面页，包含：
      - 举报队列：芯片筛选待处理 / 已处理，以及举报类型。
      - 详情：举报原因、快照、上下文、被举报对象的历史。
      - 操作按钮：红色只用于封禁、删除这类危险操作，并要二次确认。
      - 审计日志。
      - 以后再加：K2 指标、K7 反馈。
  - **隐私**：管理员看不到任何聊天内容，被举报的快照除外。
- **工作量**：L
- **依赖与风险**：权限设计是关键。要写攻击测试：普通用户调用任何 admin RPC 都必须失败；管理员也读不到没被举报的私聊。
- **和现有功能的关系**：`reports`、`report_circle`、`report_circle_post`、发现页、A1、G10。

#### K3 监控与告警 【需决定】是否用第三方

- **用户价值**：定时任务停了、推送大量失败、某个函数报错激增、AI 额度用光时，你第一时间知道。
- **参考**：Sentry、Better Stack、Healthchecks.io；Supabase Metrics 加 Grafana Cloud。
- **实现思路**：
  - **内部检查**：新表 `ops_checks`。`run_later_dispatch()` 每分钟顺带写一次心跳，并检查：
    - `cron.job_run_details` 最近有没有失败；
    - `push_deliveries` 的失败率；
    - `client_errors` 有没有突增；
    - `ai_usage` 是否接近上限。
    - 发现异常就写入 `ops_alerts`，并推送给管理员。
  - **外部心跳（可选）**：接一个免费的心跳监控（Healthchecks.io），用来发现「整个 cron 都不跑了」。需要你注册账号。
  - **函数错误（可选）**：Edge Functions 接 Sentry 免费档（`npm:@sentry/deno`），严格脱敏。
- **工作量**：M
- **依赖与风险**：
  - 用不用第三方需要你定，涉及数据出境和隐私。
  - 不允许对线上跑探测脚本，外部监控只做被动心跳。
- **和现有功能的关系**：错误报告、调度器、K1。

#### K4 功能开关与灰度 + 最低版本

### L 性能、离线、无障碍、国际化

#### L1 拆分聊天页并建立扩展点

- **用户价值**：用户不会直接看到变化。但之后每个聊天功能都开发得更快、合并冲突更少、重建也更少。
- **参考**：工程项，没有对应的产品功能。
- **实现思路**：

- **依赖与风险**：会和任何改聊天页的功能冲突，所以在第 1 批独占聊天页，同批的其他功能不碰这些文件。

#### L2 存储空间管理

- **用户价值**：知道 App 占了多少空间、哪个聊天最占地方，可以一键清理缓存，或设置「自动清理 30 天前的媒体缓存」。
- **参考**：Telegram 存储用量（按聊天、按类型，可自动删除）；WhatsApp 管理存储（2026 年起可以按聊天找大文件）；微信存储空间。
- **实现思路**：纯客户端。
  - 统计本机缓存的大小，按会话分组：SQLite 缓存、图片缓存、文件预览缓存、文字识别缓存、壁纸文件。
  - 清理只删本机缓存，不影响服务器。
  - 网页显示 IndexedDB 的用量（`navigator.storage.estimate`）。
- **工作量**：S/M
- **依赖与风险**：清理后重新下载会耗流量，要提示用户。
- **和现有功能的关系**：离线缓存、文件预览缓存。

#### L3 离线搜索（本地全文索引）

- **用户价值**：没网时也能搜到本地缓存过的聊天；这也是以后私密聊天（G9）的搜索方案。
- **参考**：Signal 和 WhatsApp 的消息是端到端加密的，搜索都在本机完成。
- **实现思路**：
  - 对本地缓存的消息建 SQLite FTS5 索引。iOS/macOS 的系统 SQLite 带 FTS5；Android 自带的版本可能没有，要用 `sqlite3_flutter_libs`。
  - 中文切分和服务器的 `search_split_cjk` 保持一致，用二元切分。
  - 网页在 IndexedDB 上做一个简单的倒排索引。
  - 搜索页没网时自动切到本地结果，并标注「仅本机缓存」。
- **工作量**：M
- **依赖与风险**：索引要和缓存同步：消息撤回或过期时要删掉对应索引。
- **和现有功能的关系**：离线缓存、全局搜索、G9。

#### L4 大文件断点续传 【花钱】

- **用户价值**：大文件上传失败了不用从头再来；也为会员的大文件上限做准备。
- **参考**：Telegram 的大文件分片上传；Google Drive、Dropbox 的可续传上传。
- **实现思路**：
  - 用 Supabase Storage 的 TUS 断点续传接口：用现成的 `tus_client` 类库，或自己写。
  - 上传可以暂停和继续；App 重启后自动续传。
- **工作量**：M
- **依赖与风险**：单个文件超过 50MB 需要升级 Supabase 套餐，并调整全局上限；还有存储费用。
- **和现有功能的关系**：文件发送、相册上传、J1。

#### L5 网页 WebAssembly 构建试验

- **用户价值**：网页版更流畅。Flutter `--wasm` 用 skwasm 渲染；Safari 从 18.2 起支持 WasmGC。
- **参考**：工程项；按 Flutter 官方的 WebAssembly 构建指南做。
- **实现思路**：

#### L6 大群 / 大圈子压测与优化

- **参考**：Discord 大服务器的成员列表按需加载；Telegram 超级群支持 20 万人。
- **实现思路**：

- **和现有功能的关系**：L11、成员列表、通知。

#### L7 关怀模式（长辈模式）

- **用户价值**：家里长辈用起来不费劲：大字、大按钮、只保留常用功能，还可以朗读文字消息。
- **参考**：微信关怀模式（大字、高对比、听文字消息）。
- **实现思路**：设置 → 外观 →「关怀模式」：
  - 文字放大到 1.3 倍。布局已经通过 1.6 倍和 2.0 倍的检查。
  - 隐藏圈子栏和不常用的入口，只留消息、通讯录、朋友圈。
  - 加大点击区域。
  - 长按文字消息可以「朗读」：用 `flutter_tts`，iOS 和 macOS 走系统 TTS，网页用 `speechSynthesis`。
  - 以后可以让家人帮长辈远程开启。
- **工作量**：M
- **依赖与风险**：字体和 TTS 声音要在真机上测试。
- **和现有功能的关系**：大字号布局检查、高对比度、减少动画、语音转文字。

#### L8 无障碍 2.0

- **用户价值**：读屏用户能知道图片里是什么；视频有字幕；色弱用户能分辨在线状态；不改系统设置也能调字号。
- **参考**：Mastodon 的图片描述；Facebook 自动替代文字；Telegram 的应用内字号。
- **实现思路**：
  - **图片描述**：发图时可以填描述，存在附件元数据里，读屏会朗读。可选让 AI 生成建议，但需要支持图片的模型。
  - **在线状态加形状**：请勿打扰显示横线，闲置显示月牙。
  - **应用内字号**：设置 → 外观加「聊天字号」滑块，独立于系统设置。
  - **视频字幕**：复用转写，在 iPhone/Mac 本机生成字幕。
- **工作量**：S/M
- **依赖与风险**：AI 图片描述依赖模型，和 F7 是同一个决策。
- **和现有功能的关系**：无障碍守卫测试、`PresenceDot`、转写。

#### L9 繁體中文界面

- **用户价值**：服务港台和海外华人用户。
- **参考**：微信、QQ、Telegram、LINE 都提供繁体中文界面。
- **实现思路**：
  - 用 OpenCC（简转繁，台湾和香港用词）从 `zh/*.dart` 生成 `zh_hant/*.dart` 初稿。
  - 人工校对术语：朋友圈、圈子、接龙等，保留原词或换成当地习惯。
  - `tr()` 支持 `zh-Hant` 语言代码。
  - 覆盖率测试推广到每种语言；推送文字也跟随语言。
- **工作量**：M
- **依赖与风险**：需要母语者校对。
- **和现有功能的关系**：翻译体系、`translations_test`、`zh_coverage_test`。

#### L10 日语 / 韩语界面

- **用户价值**：AI 翻译已经支持日语和韩语，界面也跟上。
- **参考**：LINE、Kakao、Discord、Telegram 都有日语和韩语界面。
- **实现思路**：沿用 L9 的多语言框架，由 AI 起草译文，母语者校对。
- **工作量**：每种语言 M。
- **依赖与风险**：长期维护成本高：每加一句文案，就要多一种翻译。建议等 L9 跑顺再做。
- **和现有功能的关系**：同 L9。

#### L11 Realtime 私有化（迁到数据库广播） 【需决定】需线上验证

- **用户价值**：用户不会直接感受到。好处是更安全（可以关掉 Realtime 的「允许公共访问」），也更省资源。
- **参考**：Supabase 官方推荐的 Broadcast from Database（`realtime.broadcast_changes`）加私有通道。
- **实现思路**：
  1. 先在托管环境实测：私有通道上的 postgres_changes 是否受影响。
  2. 逐张表用触发器把变更广播到 `room:<conversation_id>` 和 `user:<uid>`；给 `realtime.messages` 写基于成员关系的访问策略。
  3. 客户端逐个从 `onPostgresChanges` 换成广播。共 54 处调用、约 24 个公共通道。
  4. 全部换完之后，再关闭「Allow public access」。
- **工作量**：L
- **依赖与风险**：
  - 访问权限只在加入通道时检查，所以把成员移除后，旧的订阅可能短时间内仍然有效。
  - 触发器会增加写库的开销。
  - 这一步只能在线上验证，需要你安排验证时间。
- **和现有功能的关系**：几乎所有实时功能都会受影响。

## 6. 为什么这样排

1. **信任底座先行**：
   - 网页版已经公开，任何人都能注册，可是举报没人处理、也没有平台管理员。这是当前最大的风险。App Store 准则 1.2 也明确要求有举报和处理。
   - 所以 K1 放在第 1 批。
   - A1 放在第 2 批，因为它要用到 L1 拆出来的消息菜单，也要用到 K1 的平台队列。
2. **先拆聊天页**：
   - 第 2 批有 5 个包都要改聊天页。
   - 先由 L1 单独占着聊天页做拆分，并建好注册表和附注槽。之后的并行冲突就从「大家改同一个 8000 行的文件」，变成「各改各的小文件」。
3. **高频、低成本的优先**：
   - 聊天分组、免打扰时段、日程、群已读名单、自动翻译、表情包，都是每天用得到的。
   - 它们不需要第三方费用，而且大多复用已有数据：`last_read_message_id`，活动、任务、提醒，AI 函数。
4. **复用已有基础设施，换更大的价值**：
   - 表单是接龙和投票的泛化。
   - @AI 复用机器人身份和 AI 函数；每日速览复用补课总结和调度器。
   - 数据看板复用成员表和审计日志。
5. **花钱和要账号的事往后放，单独列出**：会员、直播、录制、原生推送、端到端加密，都要你先拍板（见第 7 节）。
6. **并行友好**：
   - 每批按目录分工。
   - 第 1 批只有 L1 碰聊天页；第 2 批开始，聊天页已经有了扩展点。
   - 同一批里，改同一个 SQL 函数的功能只放一个（例如 C1 和 C4 分在两批）。

## 8. 开工须知（给实现 session）

### 8.1 迁移编号

- **起点**：线上最新编号是 `202610200010`，新迁移必须比它大。
- **预分配**：
  - 第 1 批用 `20261021`，第 2 批用 `20261022`，第 3 批用 `20261023`。
  - 后四位是「包号 × 100 + 序号」：
    - 1-2 包是 `202610210100`–`202610210199`；
    - 2-6 包是 `202610220600`–`202610220699`。
  - 包内按 10 递增，留出插入的空位。
- **之后的批次**：第 4 批起用 `20261024`、`20261025`……也可以用开工当天的真实日期，只要比线上最新编号大，并且批内不冲突。
- **推送**：`db push` 时，如果本地有比线上最新编号还早的迁移，要加 `--include-all`。同一批的包按编号顺序合并，可以少遇到这种情况。

### 8.2 改函数前，先找最新定义

```sh
grep -lE "function public\.<函数名>\(" supabase/migrations/*.sql | sort | tail -1
```

被重定义过多次的高风险函数：

| 函数 | 版本数 | 最新定义所在的迁移 |
|---|---|---|
| `claim_push_delivery` | 7 | `202610200010_push_text_language.sql` |
| `run_later_dispatch` | 4 | `202610190021_moments_push.sql` |
| `search_messages` | 4 | `202610160044_search_messages_rpc.sql` |
| `edit_message` | 3 | `202610130024_channel_webhooks.sql`（之后还有锁定编辑的触发器，如 `messages_review_lock_edit`） |
| `create_moment` | 2 | `202610190022_moments_video.sql` |
| `toggle_message_reaction` | 2 | `202610130026_circle_emojis.sql` |

优先用**触发器、新函数或在 Edge Function 里过滤**来扩展，少重写旧函数。例如 A2 用触发器写历史，A4 在 `push` 函数里过滤。

### 8.3 容易被覆盖的规则（重写任何函数时逐条核对）

- 限时消息的过期过滤：`expires_at`、`expired`。
- AI 守护的 `review_state`：`message_visible_to_current_user`，以及 `202610170091_ai_guard_hidden.sql`。
- 文件传输助手：没有已读、没有正在输入、不计未读、不推送。
- 相册计数：同一个 `attachment_group_id` 的一组算一条。
- 资料可见范围：`visible_profile_*`、`can_view_profile_details`。
- 在线状态可见性：`visible_presence`、`presence_can_see`。
- 拉黑：`are_users_blocked`。
- 推送文字按收件人的语言和时区生成。
- 私聊只限好友：`get_or_create_direct_conversation`。
- 阅后即焚：不能转发、不进相册和共享媒体。
- 存储路径：附件必须在发送者所在会话的文件夹下。

### 8.4 冲突热点和约定

- **`lib/shared/l10n/zh/zh.dart`**：每个包只追加一行 import 和一行注册。新文案放到新文件 `zh_<包名>.dart`。
- **`test/accessibility/a11y_screens.dart`**：新页面追加到末尾。
- **`lib/shared/navigation/app_router.dart`**：新路由加在末尾。
- **聊天页**：第 1 批只有 L1 可以碰。之后各功能通过 L1 建好的注册表和附注槽接入，不直接改列表、气泡和菜单的主体文件。
- **`supabase/functions/ai/`**：新动作各自放在新文件里，例如 `assistant.ts`、`digest.ts`；`request.ts` 和 `handler.ts` 只追加分支。

### 8.5 新 Edge Function 的配置

- **不带登录令牌、靠自己校验的函数**，要在 `supabase/config.toml` 里设 `[functions.<名字>] verify_jwt = false`。
  - `calendar-feed`：靠令牌。
  - `billing-apple`、`billing-google`、`billing-web`：靠签名。
  - `bot-events`：和 `scheduled-dispatch` 一样，靠共享密钥唤醒。
  - 部署时 `supabase functions deploy <名字>` 会读取这项配置。
- **`admin` 函数**：保持 `verify_jwt = true`，在函数内再查一次 `is_app_admin()`。
